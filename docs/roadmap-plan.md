日期：2026 年 11 月 10 日  
对应设计：[目标设计](roadmap-design.md)；已实现能力单独记录在 [工程设计](design.md)。
目标宿主：DeepSeek Harness（DSH），首个支持版本 `0.2.2-rc.1`（源码 `fcc0ad4621`）

本文把 stash 拆成七个阶段，并规定贯穿全程的工程基线和调试设计。每个阶段结束时都交付一个能编译、能安装、能运行的插件；后一阶段在前一阶段之上增加能力，不推翻已有结构。

## 1 名称与范围

- 项目名 stash，取 git stash 的含义：把重要的上下文暂存起来，需要时随时切回。它面向软件开发，不面向角色扮演或文学创作。
- 人看到的名字统一用 stash：插件名、`/stash` 命令、设置页与侧栏页标题、日志与 trace 的命名空间。
- 模型看到的名字保留设计文档中的 `memory_view`、`memory_write`、`<memory-context>`。对模型来说 “memory” 直接说明用途，“stash” 容易被理解成 git 操作。这些名字集中定义在一处（第 2.5 节），要改只改一处，并由快照测试暴露全部影响。
- 插件包名 `@wahhheee/dsh-stash`：scope 是作者的 npm 用户名，`dsh-` 前缀沿用 DSH 插件的命名习惯，并避开已被占用的无 scope 包名 `dsh-stash`。仓库内另外两个包 `@wahhheee/stash-core`、`@wahhheee/stash-devtools` 设为 `private`，不发布。
- 许可证 MIT，与上游 DSH 相同。
- 不做原型。设计中依赖、但尚未验证的宿主行为，列为对应阶段的“宿主确认项”，在该阶段开头确认，并写明确认失败时的退路。

## 2 工程基线

第一阶段就定下来，之后各阶段沿用。

### 2.1 仓库结构

```text
stash/
├── package.json             pnpm workspace 根（private）
├── pnpm-workspace.yaml
├── LICENSE                  MIT
├── AGENTS.md                本仓库的开发准则（只写现状）
├── CHANGELOG.md             每个阶段一个版本条目
├── docs/
│   ├── design.md            设计文档（只写现状）
│   ├── decisions/           决策记录（历史型载体）
│   └── debugging.md         调试手册
├── packages/
│   ├── core/                纯领域逻辑，不依赖 DSH
│   ├── plugin/              DSH 插件包：Host 面、Client 面、cordis.patch.yml
│   └── devtools/            离线检查工具、测试夹具、端到端测试封装（不发布）
└── e2e/                     端到端场景
```

依赖方向只能是 `plugin → core`、`devtools → core`、`devtools → plugin`。`core` 不允许引入任何 `@deepseek-ai/*` 包，由 lint 的 `no-restricted-imports` 规则强制。用户只安装 `plugin`；`core` 在构建时打进插件包，不单独发布。

`plugin` 内部再分三层：`src/adapters/` 每个文件封装一类 DSH API，实现 `core` 定义的端口；`src/host/` 把端口实现、工具、注入、投影、命令组装起来；`src/client/` 是界面。DSH 的公开 API 目前处于 pre-stable 阶段（DSH 仓库 `AGENTS.md`），宿主升级带来的改动应只落在 `adapters/`。

### 2.2 core 的模块

| 模块        | 内容                                                                  |
| ----------- | --------------------------------------------------------------------- |
| `namespace` | 路径解析：`/`、`./`、`../`、会话短 ID；相对路径在调用时解析为绝对引用 |
| `refs`      | `dsh://` 与 `dsh-session:` 引用的解析与生成                           |
| `rules`     | `RULES.md` 解析：去掉来源注释、展开 `@` 并入、预算检查                |
| `notes`     | frontmatter 解析与校验；未知 `type` 与未知字段原样保留                |
| `index`     | 索引渲染与三步折叠                                                    |
| `resident`  | 常驻快照组合、“看得到的版本”的折叠、比对与注入决策                    |
| `commits`   | 会话记忆提交的折叠，与提交载体无关                                    |
| `history`   | 轮次预览、事件窗口、压缩摘要、搜索结果的渲染；时间窗换算              |
| `switches`  | 三级开关的生效计算                                                    |
| `templates` | 全部模型可见文字（第 2.5 节）                                         |
| `trace`     | trace 事件的类型定义                                                  |
| `ports`     | 端口定义（第 2.3 节）                                                 |

### 2.3 端口：把可能变化的地方隔离出来

| 端口                                           | 首版实现                                  | 预见的变化                              |
| ---------------------------------------------- | ----------------------------------------- | --------------------------------------- |
| `SessionLogPort`：读日志、事件窗口、按条件过滤 | DSH `ctx.sessionQuery`                    | DSH API 变动；其他宿主                  |
| `SurfacePort`：可见节点、来源化消息的注入      | DSH `session.surface` 与 `agent/pre-step` | 同上                                    |
| `WorkspacePort`：工作区与会话归属              | DSH `ctx.workspaceRegistry`               | 多目录归属同一工作区                    |
| `MemoryStore`：工作区记忆读写、锁、修改日志    | 本地 Markdown 与 `.journal.jsonl`         | 同步盘、远程存储                        |
| `CommitCarrier`：会话记忆提交的写与读          | 工具结果 `meta`，PTC 下 `deferContext`    | 插件自有日志事件（设计第 5.3 节方案 B） |
| `HistorySearch`                                | 时间窗收窄加字面扫描                      | trigram 全文索引、语义检索              |
| `TokenEstimator`                               | DSH `ctx.tokenMeter`                      | 其他模型的分词器                        |
| `SwitchStore`                                  | 插件配置、`workspace.json`、DSH 存储域    | 新增层级                                |
| `TraceSink`                                    | JSONL 文件与宿主日志器                    | OpenTelemetry（DSH 已有 `dsh-otel`）    |
| `Clock`、`IdGen`                               | 系统时间、随机 ID                         | 测试中注入固定值                        |

每个端口在 `plugin/src/adapters/` 有一个 DSH 实现，在 `core` 的测试中有一个内存实现。`core` 的全部逻辑因此能脱离 DSH 单独测试。

### 2.4 数据格式与版本

| 数据                                               | 版本字段                               |
| -------------------------------------------------- | -------------------------------------- |
| `workspace.json`、`.stats.json`、`.redirects.json` | `format`                               |
| `.journal.jsonl`、trace 文件的每一行               | `v`                                    |
| 注入消息的 `source` 元数据、工具结果的 `meta`      | `stash.v`                              |
| 会话开关记录（DSH 存储域）                         | `v`                                    |
| 笔记与规则的 frontmatter                           | 不设版本：字段只增不改义，未知字段保留 |

规则：

- 读取端兼容所有已发布的版本，写入端只写当前版本。
- 需要改变含义时增加版本号并写迁移；迁移只向前，写入前先备份。
- 读到比当前版本新的数据时拒绝写入并明确报错，不降级覆盖。
- 会话日志只追加，其中的 `meta` 和 `source` 无法迁移，所以投影必须永久识别所有历史版本。
- 预留字段：规则 frontmatter 的 `paths`（路径作用域规则，1.0 之后）。首版遇到时拒绝写入并说明暂不支持，避免它被当成无条件规则，扩大适用范围。

### 2.5 模型可见文字

- 全部集中在 `core/templates`：静态说明、工具名、schema 与描述、快照与各类通知、工具结果的框架文字、错误信息、`/.guide.md`。其他代码不得出现模型可见的字符串，由测试检查。
- 快照测试：每个模板对固定输入渲染，结果连同 token 估算值存为快照文件。任何模型可见文字的改动都在评审中以 diff 呈现，token 增长一目了然。
- 前缀稳定性测试：对两个工作区的两个会话渲染静态说明与工具 schema，断言逐字节相同。
- 模板按已实现的能力组装：某阶段尚未提供的功能，不出现在静态说明里。
- 语言规则按设计第 9.4 节：框架文字用英文，内容保持原文。

### 2.6 配置

设计第 10.4 节的字段随功能所在阶段加入，另加调试用的 `trace`（`off`、`metadata`、`content`）和 `traceRetentionDays`。全部是校验过的配置字段；运行中可安全修改的标为可热更新，在 DSH 插件设置页直接改。不用隐藏的默认常量，这也是 DSH 对插件的约定。

### 2.7 错误

- 工具失败返回稳定的错误码，例如 `STASH_STALE_READ`、`STASH_BUDGET_EXCEEDED`、`STASH_PATH_NOT_WRITABLE`、`STASH_UNSUPPORTED`、`STASH_MEMORY_OFF`，附一句给模型的英文说明和下一步建议。
- 给用户看的原因放进 DSH 工具结果的 `error.reason`，不进模型上下文。
- 内部异常写日志和 trace，带调用 ID；不吞掉，不伪装成空结果。
- 必需的宿主服务缺失（例如没有挂载 `ctx.sessionQuery`）时，加载即报错，不静默降级。

### 2.8 宿主兼容

- `engines.dsh` 写明支持的 DSH 版本范围，起始为 `>=0.2.2-rc.1 <0.3.0-0`。DSH 检查这个范围时打开了 semver 的 `includePrerelease`（`packages/boot/app-boot/src/plugin-compatibility.ts`），写成 `<0.3.0` 会放行 `0.3.0-rc.*` 这类预发布版，所以上限写 `<0.3.0-0`。用到的 `@deepseek-ai/dsh-*` 包同时列在 `peerDependencies` 和 `devDependencies`，这是 DSH 发布教程对外部插件的要求。
- 宿主契约测试：把 stash 依赖的宿主行为写成测试，宿主升级时先跑。首批包括：
  - 分叉复制前缀事件，seq 不变；
  - 压缩以 `surfaceOp: replace` 替换可见节点，原事件仍可读；
  - 工具结果裁剪后 `meta` 仍在；
  - `agent/pre-step` 中加入的来源化消息被记入日志；
  - 按 agent 作用域注册的段落和工具只对该会话可见。
- CI 对锁定的 DSH 版本（首个为 `0.2.2-rc.1`）必须通过；另有一个任务跑最新的 DSH 预发布版，失败只报警，用来提前发现宿主变化。
- 升级流程：改 `engines.dsh`，跑契约测试，只改 `adapters/`，跑全量测试，记入 CHANGELOG。

### 2.9 CI 与开发期分发

- CI 用 GitHub Actions。私有仓库的 Actions 分钟数有额度，Windows 和 macOS 运行器按倍数折算（按 GitHub 目前的规则分别为 2 倍和 10 倍，以其计费页为准），因此：
  - 每次推送和 PR：Linux 上跑全部自动化测试；Windows 只跑单元、宿主集成和一组端到端冒烟，作者的日常环境是 Windows，这部分不省。
  - 每晚或手动触发：Windows 全量端到端、macOS 冒烟、最新 DSH 预发布版的兼容任务。
- 行为评估需要 DeepSeek API key，放在仓库 secret 中，只手动或定时触发，不在 PR 中运行。
- 开发期不发布到 npm。安装方式：本地检出用 `dsh plugin --profile <名称> add ./packages/plugin` 链接；给别的机器试用时，用 `pnpm pack` 生成的 tarball 安装。每个阶段的退出条件都包括“从 tarball 装进全新 profile”，与将来从 npm 安装走同一条路径。

### 2.10 文档与提交

- `AGENTS.md`：开发命令、目录说明、本节的约定。
- `docs/design.md`：只描述现状；设计变化的原因和经过写进 `docs/decisions/`。
- `docs/debugging.md`：第 3 节的操作手册。
- `CHANGELOG.md`：每个阶段一个版本条目，阶段 1 至 6 依次为 `0.1.0` 至 `0.6.0`，阶段 7 为 `1.0.0`。
- 提交信息写变化和原因；代码注释与文档写现状（设计第 3.2 节）。

## 3 调试与可观测性

目标：功能问题都能在不打开 GUI、不截图的情况下复现和定位。必须在 GUI 中才出现的问题，用户也能用一条命令导出文本材料。

### 3.1 `/stash` 命令

DSH 的人类命令（`ctx.commands`）直接执行，不产生模型消息，不进入模型上下文，输出是纯文本，可以直接复制。

| 命令                                  | 输出                                                                                                 | 首次可用                 |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------ |
| `/stash status`                       | stash 与 DSH 版本、生效开关及其来自哪一级、工作区 ID 与记忆目录、规则与索引用量、trace 状态          | 阶段 1                   |
| `/stash doctor`                       | 检查记忆根目录权限、DSH 版本是否在范围内、必需服务是否在、锁文件残留、修改日志完整性、投影缓存一致性 | 阶段 1，随阶段补充检查项 |
| `/stash doctor --bundle`              | 生成问题报告包（第 3.6 节）                                                                          | 阶段 1                   |
| `/stash context`                      | 当前会话“模型看得到的版本”与“当前实际版本”的渲染文本、token 数、两者差异                             | 阶段 2                   |
| `/stash render`                       | 如果现在注入，完整快照的确切文本                                                                     | 阶段 2                   |
| `/stash explain [n]`                  | 最近 n 次注入决策：请求位置、情形（完整、增量、不注入）、原因、各部分哈希                            | 阶段 2                   |
| `/stash trace off\|metadata\|content` | 切换 trace 级别                                                                                      | 阶段 1                   |
| `/stash health`                       | 健康信号（设计第 8.9 节）                                                                            | 阶段 6                   |
| `/stash rollback <整理会话>`          | 回滚一次整理                                                                                         | 阶段 6                   |

### 3.2 日志与 trace

- 日志：用宿主的日志器，命名空间 `stash`，级别可配置。
- trace：写入 `$DSH_HOME/memory/.trace/<日期>.jsonl`，一行一个事件，按天轮转，按 `traceRetentionDays` 清理。默认只记元数据：会话 ID、seq、哈希、token 数、耗时、决策、错误码；设为 `content` 时才记正文。
- 事件类型：`inject.decide`、`inject.emit`、`tool.view`、`tool.write`、`commit.fold`、`external.detect`、`switch.change`、`lock.wait`、`error`。字段类型定义在 `core/trace`，与文件共用一个版本号。

### 3.3 离线开发工具（devtools）

在 stash 仓库里运行（`pnpm devtools <命令>`），读取一个 DSH 主目录或它的副本，默认只读，`--write` 时才写：

| 命令               | 用途                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| `fold <会话>`      | 列出会话日志中的全部记忆提交，以及每一步之后的会话记忆状态             |
| `reconcile <会话>` | 在日志中每个请求边界重放注入决策，与实际注入的消息逐条对比，列出不一致 |
| `render <工作区>`  | 输出常驻快照文本与各部分的 token 数                                    |
| `view <路径>`      | 离线得到与 `memory_view` 相同的输出                                    |
| `journal <工作区>` | 浏览修改日志，按整理会话分组，可导出任意旧版本                         |
| `verify`           | 检查记忆目录、修改日志、重定向表、投影缓存是否一致                     |

`reconcile` 最关键。用户遇到“规则没生效”“重复注入”这类问题，开发者拿到会话日志，就能在本地复现注入决策的全过程。devtools 读会话日志用 DSH 自己的持久化与查询包（只读），不自己解析文件格式。

### 3.4 自动化端到端

- **环境。** 每个测试一个临时 DSH 主目录，用锁定版本的真实 `dsh` 可执行文件（devDependency），启动一个装了 stash 的 profile。
- **模型。** 用 DSH 的 `dsh-llm-mock-server` 代替真实模型：经 `DEEPSEEK_BASE_URL` 指向它，脚本化文本回复和工具调用，并捕获每个请求。断言直接针对捕获到的请求内容：系统提示、工具声明、注入的消息。它的工具名和参数是服务器级配置；需要多步、每步调用不同工具时，stash 测试里加一层按请求顺序返回脚本的薄封装，沿用同一 SSE 格式。
- **回归。** 需要真实模型行为时，用 `dsh-llm-replay` 重放录制好的会话：录制一次需要 API key，之后在 CI 中无 key 重放。
- **驱动。** 多轮对话、`/compact`、`/stash …` 用 `dsh-sdk-client`（stdio JSON-RPC）；单轮冒烟用 `dsh-loader-smoke`。
- **压缩。** 用 `/compact`，或在测试 profile 中调低 `dsh-compaction-basic` 的 `thresholdRatio`，按需触发。
- **故障注入。** 在宿主集成测试中替换 `MemoryStore`、`CommitCarrier` 的实现，在写入的每个环节抛错或中断，检查恢复结果。故障注入只存在于测试代码，不进入发布的插件。

### 3.5 DSH 自带的调试手段

- `dsh --profile <名称> --dump-config`：确认 stash 层已装上、配置已生效。
- 开发用 profile 启用 DSH 的开发者工具包（`inspector-profile`）：用 Chrome DevTools 连接宿主与客户端，打断点、看控制台和网络；侧栏里有原始会话日志查看器。
- 开发循环：`dsh plugin --profile stash-dev add ./packages/plugin` 链接本地检出，构建监听模式下改代码。宿主代码能否热重载，在阶段 1 确认；不能则重启 profile，客户端代码重建后刷新页面。

### 3.6 问题报告包

`/stash doctor --bundle` 在 `$DSH_HOME/memory/.reports/` 下生成一个压缩包，内含：stash 与 DSH 版本、生效配置（去掉凭据）、生效开关、最近的 trace（默认不含正文）、`doctor` 的检查结果，以及用户勾选附带的会话日志。用户提交这一个文件，开发者用 devtools 复现，不需要截图。

### 3.7 测试分层

| 层       | 工具                                         | 覆盖                                                         | 何时跑                 |
| -------- | -------------------------------------------- | ------------------------------------------------------------ | ---------------------- |
| 单元     | vitest 与 `core` 的内存端口                  | 解析、渲染、折叠、比对、开关计算、模板快照                   | 每次提交               |
| 宿主集成 | `dsh-tool-testkit`、`dsh-agent-loop-testkit` | 工具、注入、投影、命令在真实 Cordis 上下文中的行为；故障注入 | 每次提交               |
| 客户端   | `dsh-client-test-runtime`（jsdom）           | 按钮、菜单、开关、记忆页                                     | 每次提交               |
| 端到端   | 真实 `dsh`、mock 模型、临时主目录            | 设计第 13.1 节的确定性验收                                   | 每次提交               |
| 宿主契约 | 同端到端                                     | 第 2.8 节列出的宿主行为                                      | 每次提交，及宿主升级时 |
| 行为评估 | 真实 API、固定任务集、重复运行               | 设计第 13.2 节                                               | 手动或定时，需要 key   |

GUI 手动检查只用于视觉和交互，不承担功能验证。

## 4 阶段总览

| 阶段                 | 交付                                                             | 结束时用户能做什么                       |
| -------------------- | ---------------------------------------------------------------- | ---------------------------------------- |
| 1 骨架               | 能编译、能安装的插件；工程基线；`/stash status`、`/stash doctor` | 装上插件，确认它在运行，且不影响模型请求 |
| 2 工作区记忆与常驻层 | 工作区规则和笔记的读写；常驻注入、增量与压缩后恢复               | 说一次“以后……”，所有会话都遵守           |
| 3 原始记录与引用     | 会话清单、轮次、事件窗口、压缩摘要、字面搜索；复制引用           | 在新会话里找回昨晚的讨论                 |
| 4 会话记忆与分支     | 会话规则与笔记、分叉继承、谱系                                   | 各分支记各自的，互不干扰                 |
| 5 开关与记忆页       | 三级开关、只读、隐私会话；输入框开关与记忆页                     | 在界面上控制、查看、编辑记忆             |
| 6 增长与整理         | 健康信号、整理会话、重定向、回滚                                 | 记忆多了可以整理，整理错了可以撤回       |
| 7 评估与 1.0         | 行为评估、规模与故障测试、文档、正式发布                         | 使用正式版                               |

依赖关系：阶段 2 依赖 1；阶段 3、4 都只依赖 2，彼此独立，可以并行；阶段 5 依赖 2 至 4；阶段 6 依赖 5；阶段 7 依赖全部。

每个阶段的共同退出条件：CI 全绿（lint、类型检查、单元、宿主集成、客户端、端到端、宿主契约）；能装进一个全新的 profile；文档描述的是现状；CHANGELOG 有该阶段条目。下文只列各阶段特有的条件。

## 5 各阶段

### 阶段 1：骨架与可安装插件

- 宿主面：配置 schema（本阶段只有 `trace`、`traceRetentionDays`、`memoryRoot`）、日志器、trace 写入、`/stash status`、`/stash doctor`（含 `--bundle`）、`/stash trace`。
- 客户端面：中英文语言包；右侧栏一个 “stash” 页，显示插件版本和宿主连接状态，用来证明客户端模块被加载、能与宿主通信。
- `core`：模块骨架、全部端口定义及内存实现、模板与快照测试框架。
- `devtools`：`verify` 命令。
- 端到端测试框架（第 3.4 节）及第一批用例。
- 文档：README、`AGENTS.md`、迁入的 `docs/design.md`、`docs/debugging.md` 初稿、CHANGELOG。

**宿主确认项**

| 确认                                                                                | 失败时的退路                                                                       |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 外部包能注册 Remote API（DSH 的 `@Remote` 依赖 typert 生成流程），客户端能调用      | 客户端改为读取对客户端可见的会话投影获得状态，操作通过程序化执行 `/stash` 命令完成 |
| SDK 能执行插件注册的命令                                                            | 命令在宿主集成测试中直接通过 `ctx.commands` 调用；端到端只经 Web 协议测试          |
| 能按 agent 作用域注册提示段落和工具（阶段 2、5 依赖它实现“开始即关闭等效于未安装”） | 全局注册并在调用时拦截；同时把“等效于未安装”降级为已知限制，带回设计讨论           |

| 桌面版能安装本地链接的插件                                                          | 桌面版只做发布包安装测试                                                           |

**退出条件**

- 本地链接与 `pnpm pack` 生成的 tarball 两种方式都能装进全新 profile；`--dump-config` 显示 stash 层。
- Web 和桌面版都能打开 “stash” 侧栏页，看到版本号与连接状态。
- `/stash status`、`/stash doctor` 在 Web 和 SDK 中返回正确文本；`--bundle` 生成的包可被 `devtools verify` 读取。
- **插件对模型请求没有任何影响**：端到端测试断言，装与不装 stash，同一对话捕获到的模型请求逐字节相同。

**不含**：任何记忆功能。

### 阶段 2：工作区记忆与常驻层

**交付**

- `core`：`namespace` 的工作区部分；`rules`；`notes`；`index`（含三步折叠）；`resident`（组合、渲染、“看得到的版本”的折叠、比对与注入决策）；模板（只涉及工作区的静态说明、完整快照、增量通知、压缩范围行、工具结果、错误信息）；经 `TokenEstimator` 的预算检查。
- `MemoryStore` 的 DSH 实现：`$DSH_HOME/memory/<WorkspaceId>/` 下的 Markdown 文件；锁文件；原子写入；含全文的修改日志；请求前按 mtime 与哈希发现外部编辑；`workspace.json`（格式版本、最后已知路径与标题）。
- 注入器：`agent/pre-step` 监听，来源化消息，按可见状态比对，完整快照、增量通知、不注入三种决策，压缩后恢复并附压缩范围行。
- 静态说明与两个工具按 agent 作用域注册。开关策略在本阶段固定为“开”；它是一个独立组件，阶段 5 换成真实的开关来源，其他代码不变。
- `memory_view`：`/RULES.md`、`/notes/**`、`/.guide.md` 与目录清单。
- `memory_write`：工作区路径上的全部操作，包括先读后改的校验、预算拒绝、常见密钥格式检查，以及 `replace` 返回被删除的行。
- `/.guide.md` 的工作区部分，含 description 的写法与“一篇一事”（设计第 8.2 节）；静态说明里对应的一句。
- 命令：`/stash context`、`/stash render`、`/stash explain`。
- 配置项：`rulesBudgetTokens`、`indexBudgetTokens`、`externalRuleUpdates`、`viewBudgetTokens`。
- devtools：`render`、`view`、`journal`、`reconcile`（工作区部分）。
- 行为评估框架，以及首批任务：持续规则的遵守；局部例外不被扩大；只读索引能否照做，以及新写的 description 是否为结论。

**宿主确认项**

| 确认                                           | 失败时的退路                                                     |
| ---------------------------------------------- | ---------------------------------------------------------------- |
| 外部插件可以通过声明合并加入自己的消息来源类型 | 改用 DSH 已有的通用来源类型，把 stash 的元数据放在其可扩展字段里 |
| `ctx.tokenMeter` 可供插件做估算                | `TokenEstimator` 改用本地近似分词，并在快照测试中与 DSH 估算校准 |

**退出条件**（端到端，断言针对捕获到的模型请求）

- 会话首个请求含完整快照；两个工作区、两个会话的静态说明与工具 schema 逐字节相同。
- 模型通过工具写入规则后，后续请求不重复注入。
- `/compact` 之后的下一个请求含最新的完整快照与压缩范围行。
- 用户在编辑器里改 `RULES.md`、另一会话写入规则：运行中的会话在下一个请求收到增量；差异超过预算一半时改为完整快照。
- 超预算的写入被拒并返回用量；索引超预算时按三步折叠，快照写明已折叠。
- 两个进程同时写同一文件：后到者得到 `STASH_STALE_READ`，文件不交错；修改日志能还原任意旧版本。
- 对上述端到端产生的会话日志跑 `devtools reconcile`，全部判定一致。

**不含**：`./` 会话路径（返回 `STASH_UNSUPPORTED`）、`/sessions`、开关界面。

### 阶段 3：原始记录与引用

**交付**

- `core`：`refs`（`dsh://`、`dsh-session:`）；会话短 ID；`history`（轮次预览、事件窗口的简略与完整两种渲染、压缩摘要、搜索结果及其覆盖范围与零结果状态）；时间窗换算；分叉前缀的去重指纹。
- 带时间的轮次投影：注册到 `ctx.sessionProjections`，检查点由投影缓存持久化。
- `SessionLogPort`、`WorkspacePort` 的 DSH 实现；用 `isCompactCheckpointSource()` 识别压缩摘要。
- `HistorySearch` 的字面扫描实现：必须收窄范围；工作区全量扫描要显式要求，并报告扫描了多少会话。
- `memory_view` 增加 `/sessions`、`/sessions/<id>/log/{turns,summaries,<a>..<b>}`，以及 `./log/…`（当前会话，含已压缩的部分）。用户粘贴的其他工作区完整引用可以只读访问。
- 会话可见性判断留一个接口，本阶段一律可见；阶段 5 接上“其他会话可检索本会话”开关。
- 客户端：消息操作栏的“复制引用”按钮（槽位 `conversation.chat.assistant-actions`，生成设计第 10.3 节的 Markdown 链接，链接文字跟随界面语言）；会话菜单的“复制会话引用”（`order: 460`）。
- 静态说明加入检索顺序；`/.guide.md` 加入检索一节。
- devtools：`view` 支持会话路径。
- 测量：在固态硬盘和机械硬盘上，测一个工作区一周会话量的字面扫描耗时（设计第 10.5 节第 5 项），结论写成决策记录，作为 1.0 之后是否加全文索引的依据。

**宿主确认项**

| 确认                                    | 失败时的退路                                                |
| --------------------------------------- | ----------------------------------------------------------- |
| 外部插件的投影单元能使用投影缓存        | 冷读时折叠日志，在 stash 自己的存储中缓存轮次时间线         |
| 客户端能从轮次尾部数据取得 seq 与轮次号 | 复制引用只精确到轮次结束事件，由 `memory_view` 向前补齐整轮 |

**退出条件**

- 用录制的会话夹具（含压缩和分叉）走“昨晚讨论”场景：按时间窗列会话、列轮次、读窗口、读压缩摘要均正确，引用都能解析。
- 字面搜索能命中两个字的中文词；零结果、检索失败、目标不可读三种状态可以区分。
- 分叉会话的继承前缀在搜索结果中去重，并注明另见于哪个会话。
- “复制引用”生成的链接通过客户端测试；把它粘贴进对话后，mock 模型按脚本调用 `memory_view`，读到对应窗口。
- 扫描耗时的决策记录已入库。

**不含**：全文索引。

### 阶段 4：会话记忆与分支

**交付**

- `core`：`commits`（与载体无关的提交折叠）；`namespace` 的会话部分（`./`、`../<id>/`）；常驻快照加入会话规则与会话笔记索引；“看得到的版本”加入本会话的提交；分叉位置通知；谱系判定（先看继承前缀中 stash 自己的记录，再用切口处事件的指纹匹配）。
- `CommitCarrier` 方案 A：原生执行时用工具结果的 `presentationMeta`，PTC 下嵌套调用用 `deferContext`。
- 会话记忆投影单元，注册到 `ctx.sessionProjections`。
- 读写 `./RULES.md`、`./notes/**`；只读 `../<id>/…`。
- 笔记作用域（设计第 3.1、8.5 节）：写入 `./notes/` 时附提示；会话清单 `/sessions` 显示每个会话的规则条数与笔记篇数；在 `/sessions` 下搜索时覆盖会话笔记；提升到工作区即复制为工作区笔记，`sources` 指回原处，原笔记不变。
- 静态说明加入笔记作用域的判断与“用过就提升”，`/.guide.md` 加入作用域一节。
- 界面修改会话记忆用的通知载体（设计第 5.3 节）：本阶段实现载体与投影，阶段 5 接上界面。
- 子代理只读，配置项 `subagentWrite`。
- `/stash context` 显示会话层；devtools 增加 `fold`。
- 端到端在 `standard` 和 `ptc` 两个预设下各跑一遍。

**宿主确认项**

| 确认                                           | 失败时的退路                                               |
| ---------------------------------------------- | ---------------------------------------------------------- |
| 工具结果被裁剪后 `meta` 保留（宿主契约测试）   | 投影改为按调用 ID 读取最早的原始结果事件                   |
| PTC 下嵌套调用的 `deferContext` 消息被记入日志 | PTC 预设中会话级写入返回 `STASH_UNSUPPORTED`，写进已知限制 |

**退出条件**

- 分叉：子会话的会话记忆等于源会话在分叉点的状态，之后双方互不影响。子会话首个请求与源会话共享前缀（比较捕获到的请求），只多一条位置通知。
- 重启后，会话记忆从日志投影重建，与重启前一致；删除投影缓存后结果不变。
- PTC 预设下写入的会话记忆同样能从日志重建。
- 读其他会话的会话规则，不会进入本会话的规则。
- 写入 `./notes/` 的结果带提示，写入 `/notes/` 的不带；会话清单的计数与搜索结果包含其他会话的会话笔记；提升后的工作区笔记出现在所有会话的索引里。
- 子代理写入被拒，但它能看到规则。

### 阶段 5：开关与记忆页

**交付**

- `core`：`switches`（全局是硬总闸；工作区与会话三态继承，会话优先；会话级的“其他会话可检索本会话”“继承工作区记忆”为两态）；关闭、打开、只读、干净会话的通知与快照模板。
- `SwitchStore`：全局开关是配置项 `enabled`；工作区开关存 `workspace.json`；会话开关存 DSH 存储域，按会话 ID 记录。
- 注册策略（“会话开始”指第一个请求；此前的开关变化直接生效、不发通知）：
  - 会话开始时即为关闭：不注册说明和工具。
  - 中途关闭：保留已注册的说明和工具，追加关闭通知。
  - 中途打开：补注册说明和工具，并注入完整快照。
- 只读模式；干净会话（设计第 4.7 节）：常驻组合跳过工作区规则与索引，快照带 clean 说明；把隐私开关接入阶段 3 留下的可见性接口；分叉时复制源会话的开关记录。
- 客户端：
  - 输入框工具行的会话开关（槽位 `conversation.input.left`）；
  - 工作区右键菜单中的“stash 设置”；
  - 右侧栏记忆页：查看和编辑工作区与会话记忆，会话笔记的“提升到工作区”按钮，各级开关，清空本会话记忆，删除工作区记忆（需二次确认，说明哪些数据不在删除范围内）。
- 记忆页编辑会话记忆时，走阶段 4 的通知载体。

**宿主确认项**

| 确认                       | 失败时的退路                                                                 |
| -------------------------- | ---------------------------------------------------------------------------- |
| 外部插件能声明自己的存储域 | 会话开关记录改存 `$DSH_HOME/memory/.sessions.json`，写入沿用锁文件与原子写入 |

**退出条件**

- 开始即关闭的会话：捕获到的请求与未安装 stash 的 profile 逐字节相同。
- 在空白会话里发第一条消息前切换开关：第一个请求只反映最终状态，没有任何开关通知。
- 干净会话：请求中没有工作区规则与工作区索引，工具可用；中途关闭继承时追加通知，恢复时注入完整快照。
- 中途关闭、中途打开、只读、隐私会话、开关继承、分叉复制开关，均按设计第 13.1 节对应各行通过。
- 在记忆页编辑工作区记忆，运行中的会话下一个请求收到增量；编辑会话记忆，通知被记入日志，投影结果一致。
- 客户端测试覆盖各控件的全部状态，包括全局关闭时下级开关不可用。

### 阶段 6：增长与整理

**交付**

- `core`：读取统计、健康信号、重定向解析、整理计划的格式、修改日志按整理会话分组。
- 读取次数与时间写入 `.stats.json`；索引开始折叠时，写入结果附一次整理提示；命令 `/stash health`；配置项 `unreadDays`。
- 整理会话：从记忆页的“整理”按钮启动一个新的 DSH 会话，带整理指南；模型可通过配置项 `maintenanceModel` 单独指定。流程如下：
  1. 模型读取全部笔记与健康信号，给出整理计划。
  2. 用户确认一次计划；涉及规则的改动用 `ask_user_question` 逐条确认。
  3. 执行。修改日志以该整理会话的 ID 分组。
- `/stash rollback <整理会话>`；`.redirects.json`，以及 `memory_view` 读到旧路径时的跳转。
- 静态说明与 `/.guide.md` 加入“边用边修”和“找回时补写”。
- 客户端：记忆页显示健康信号，提供“整理”按钮和回滚入口。

**退出条件**

- 在含 100 篇笔记的夹具工作区上跑一次整理（mock 模型或重放）：合并后旧路径可读并注明去向；拆分后原路径仍有效，新笔记的 `sources` 来自原笔记；未经确认的规则改动不生效；回滚后文件逐字节恢复。夹具中包含只写主题的描述和记了两个事实的笔记，整理计划应把它们列出。
- 整理后的上下文刷新符合设计第 8.9 节的表格。
- 用真实 API 跑一次整理，记录 token 与费用（手动）。

### 阶段 7：评估、加固与 1.0

**交付**

- 完整的行为评估（设计第 13.2 节），与“只有原始记录查询”的基线对比，报告：找回成功率、规则遵守率、仅凭索引的正确率、错误扩大率、虚构来源率、token、费用、延迟。
- 故障注入：写入各环节中断、锁文件残留、修改日志损坏、投影缓存丢失、DSH 主目录只读。
- 规模测试：1,000 篇笔记、数百个会话的工作区下，启动、注入、检索的耗时；机械硬盘上至少跑一次。
- 文档：用户指南（中英文）、调试手册定稿、设计文档与实现逐节核对。
- 发布 `1.0.0`：确定 `engines.dsh` 范围，写 CHANGELOG。公开仓库，并以 `npm publish --access public` 发布 `@wahhheee/dsh-stash`（scope 包默认按私有发布）；公开与发布的时间届时由作者确认。

**退出条件**

- 评估报告和已知限制写入仓库。
- 全部确定性验收通过。
- 故障注入下没有数据丢失，没有报告成功但实际未生效的情况。
