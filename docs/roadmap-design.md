> 规划参考：原始 v0.2 设计，保留未来阶段目标。当前已实现能力以 [工程设计](design.md) 为准。

首个目标宿主：DeepSeek Harness（下称 DSH），以插件形式实现。

本文定义记忆系统的目标、分层、存储、加载、检索、写入、工具面和 DSH 接入方式。第 14 节记录关键选择、理由和未采用的备选。

## 1 目标、原则与边界

### 1.1 要解决的问题

用户不必重复说过的话，具体是三件事：

1. **历史讨论可找回。** 昨晚在某个会话里讨论了一晚上方案，今天新开会话说“昨晚十一点左右我们讨论的 xxx 方案”，模型能找到原文并接着做。不要求用户或模型事先把讨论整理成文档。
2. **持续性要求自动生效。** 用户说过“此处无需校验 checksum”“以后简单修改无需回归测试”，之后工作区里的 Agent 都能看到并遵守，且保留原话的适用边界。
3. **经验跨会话复用。** 模型踩过一个并非偶然失误造成的坑，可以决定记下来，换一个会话也不再踩。

“不再重复我说过的话”是可找回、可延续的设计理念，不是让用户说过的每句话常驻上下文。

### 1.2 原则

| 原则       | 在本设计中的含义                                                                                                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AI 主导    | 查不查、查什么、记不记、记在哪由模型判断。程序负责持久化、组合、呈现和校验，不按相似度自动挑选“相关记忆”塞进上下文。唯一的例外是常驻层：它由程序保证可见，因为“应时刻遵守”的内容不能靠模型自觉去读。 |
| 可重建     | 原始会话记录永久保留且可读，上下文压缩只改变模型当前看到的视图，不删除任何事件。常驻层在压缩后自动恢复。                                                                                             |
| 单一正本   | 每类事实有且只有一个权威来源（第 5 节）。索引和目录从正本派生，可以重建。                                                                                                                            |
| 渐进式披露 | 常驻层只放规则和一行一条的索引；索引指向笔记；笔记指向原始记录。每一跳都有明确的引用，模型按需深入。                                                                                                 |
| 按需查看   | 除常驻层外，一切内容都由模型通过工具主动读取。                                                                                                                                                       |

一条推论决定了整体的克制程度：**原始记录不会丢，所以“记不记”只影响将来找回的成本，不影响能否找回。** 写记忆的门槛因此是“能明显降低将来的成本或防止出错”，而不是“不记就没了”。这也意味着压缩前不需要“抢救式保存”的仪式。

### 1.3 不做什么

- 不默认自动召回并注入片段（传统 RAG 路径）。
- 不对每轮或每个会话强制生成总结。
- 不依赖向量数据库或知识图谱。
- 不做定期自动整理（第 8.9 节）。
- 不复制会话日志作为第二份原始历史。
- 不做跨工作区自动汇总、多人权限、跨设备同步。
- 不另造 Agent，以 DSH 插件实现。

## 2 分层模型

| 层          | 内容                                       | 如何进入上下文                             | 正本                                     | 量级                            |
| ----------- | ------------------------------------------ | ------------------------------------------ | ---------------------------------------- | ------------------------------- |
| L0 常驻层   | 工作区规则、会话规则、笔记索引（每条一行） | 自动注入：会话首个请求、压缩后、外部修改后 | 工作区记忆文件；会话规则来自会话日志投影 | 合计约 5K tokens 以内（可配置） |
| L1 记忆笔记 | 经验、决策指针、背景、外部资料指针         | 模型按需读取                               | 工作区记忆文件；会话笔记来自会话日志投影 | 每篇约 100 至 800 tokens        |
| L2 原始记录 | 用户与助手消息、工具调用与结果             | 模型按需浏览或搜索                         | DSH 会话日志                             | 不限                            |
| 机械目录    | 会话列表、轮次时间线、笔记清单             | 模型按需浏览                               | 从 L1、L2 派生                           | 按查询范围                      |

L0 是“无需跳转、直接读”的部分，相当于记忆系统自己的 AGENTS.md。L1 和 L2 需要跳转。机械目录不是记忆，是让模型在没有任何笔记时也能按时间和标题定位原始记录的导航面（第 7 节）。

## 3 该记什么，记在哪里

这一节既约束记忆系统，也是一套项目维护方法。两者用同一个判断顺序。

### 3.1 写入前的判断顺序

模型准备“记下来”时，按顺序回答以下问题，第一个“是”决定去向：

1. **仓库能表达吗？** 当前实现、配置、接口行为、项目开发准则、变更原因，正本分别是代码、注释、文档、仓库 `AGENTS.md` 和 Git 历史；可复用的多步操作流程适合写成仓库里的技能文件。能写进仓库且当前指令允许，就写进仓库，不进记忆。
   - 跟这次任务有关的，可以改、整理或重构；无关的，用户没要求就别动。用户有明确要求，就按用户说的做。
   - 如果仓库不能改，又确实需要记下某个实现细节，就在笔记里写明适用版本，以及可以去哪里核实（文件路径或提交）。
   - 从零开始的项目，一开始就规划清晰的结构、提交历史、注释（或自解释的代码）、文档和 `AGENTS.md`，不把这些内容转移到记忆系统。
2. **是用户明确表达的持续性要求吗？** 写入规则（L0）。保留原话的边界词：“此处无需校验 checksum”必须带上“此处”指什么，不能扩大成“无需校验”；“简单修改无需回归测试”必须保留“简单修改”。作用域按用户的说法定：“以后”“这个项目”写工作区，“这次”“这个分支”写当前会话；“所有项目都这样”这类跨工作区的个人偏好不进记忆系统，属于 `~/.dsh/AGENTS.md`（第 14 节问题 5），模型告诉用户，用户同意后可以用普通文件工具代写，经过宿主的权限审批。范围不清且不同理解会明显改变行为时，问一句再写。
   - 新规则与仓库 `AGENTS.md` 冲突时，仓库优先（第 6.2 节）。模型应告诉用户冲突所在，并建议是否修改 `AGENTS.md`，而不是悄悄写一条无效规则。
3. **是代价高、会重现的经验吗？** 写一篇经验笔记：条件、现象、做法、证据引用。偶然笔误、立刻可见的拼写错误、读代码就知道的事不记。
4. **是形成了结论、之后可能被引用的讨论吗？** 写一条决策指针：三到五行结论加原始记录引用，不复制讨论全文。即使不写，原始记录仍可通过机械目录找到；指针只是把下次找回的成本从几次浏览降到一次读取。拿不准会不会被引用时可以不写：以后哪个会话花了较高代价从原文找回这段结论，由它补写（第 8.6 节）。
5. **以上都不是。** 不记。

**笔记写在工作区还是会话。** 第 3、4 步的笔记默认写工作区 `/notes/`。判断只问一句：离开这个会话，它还成立吗？

| 写到             | 内容                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| 工作区 `/notes/` | 踩坑经验、讨论结论、项目背景、外部资料等离开本会话仍成立的内容，占笔记的大多数         |
| 会话 `./notes/`  | 只在本会话或本分支成立的内容：分支里的临时约束、某个实验方案的进展、当前任务的工作记录 |

会话笔记只出现在本会话和之后从它分叉的会话的索引里，其他会话不会自动看到。写错到会话里的笔记，靠写入提示、跨会话可发现和用过就提升三处补救（第 8.5 节）。

### 3.2 状态型载体只写现状

文字载体分两类，规则不同：

| 类别   | 载体                                                                               | 写法                                                          |
| ------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 状态型 | 代码注释、功能文档、`AGENTS.md`、配置说明、记忆规则、记忆中的背景与经验做法        | 只描述当前事实、当前约束及其原因。不写“从 X 改成 Y”“新增 X”。 |
| 历史型 | 提交信息、缺陷记录、决策记录、更新日志、变更日志、公告、发布说明、记忆中的事件回顾 | 应当写清变化：改了什么、为什么、影响是什么。                  |

例子：

- 用户说输入框太窄，模型把宽度从 X 改成 Y，并在代码旁注释“将 X 改成 Y 避免过窄”。错误。注释若有必要，应写当前约束，例如“宽度需容纳 20 个汉字的标签”。
- 构建已支持 `windows/amd64`、`linux/amd64`，用户要求加 `linux/arm64`。在注释或文档里写“加入 linux/arm64 构建”是错误的；写“含 linux/arm64”同样错误，它只在“刚加上”的语境里才说得通。正确写法是“可选产物：`windows/amd64`、`linux/amd64`、`linux/arm64`”。
- 同一次修改的提交信息应写“构建增加 linux/arm64 产物”，因为提交信息属于历史型载体。

自检问题：**一个从没见过旧版本的读者，读到这句话是否觉得完整、准确、不突兀？** 只有在 diff 语境里才说得通的措辞（“新增”“改为”“含”“现在也支持”“不再”）都应改写。

记忆本身也遵守这条规则。规则和笔记是状态型载体，修改时原地重写为当前要求，历史由会话日志和修改日志承担（第 8.4 节）。经验笔记中“当时发生了什么”的部分属于事件回顾，可以写过程；“以后怎么做”的部分写现状。

### 3.3 方法论如何交付给模型

完整方法论较长，不适合常驻。交付分两层：

- 静态提示里放约 6 行摘要（第 9.3 节），每次请求都在缓存前缀中，几乎不增加成本。
- 完整指南作为只读文件 `/.guide.md` 放在记忆命名空间里，模型拿不准时自己去读。

## 4 作用域、命名空间与引用

### 4.1 工作区是根

记忆树的根是 DSH 的工作区（`Workspace`）。工作区有生成的稳定 ID（`WorkspaceId`），会话归属以工作区记录里的 `sessionIds` 为准，不以 `cwd` 字符串推断。DSH 首次启动时创建的“默认工作区”（`文档/default-workspace`）是普通工作区，规则相同。不属于任何工作区的会话（侧栏中的未分组会话）只有会话作用域。

工作区之下的单位是会话。分支是新会话，继承分叉点以上的内容，之后与源会话的会话记忆彼此独立。

### 4.2 命名空间

工具把记忆和原始记录呈现为一棵路径树。这些是逻辑路径，由工具解释，大部分不对应磁盘文件。

```text
/                                  当前工作区
├── RULES.md                       工作区规则（常驻）
├── notes/…                        工作区笔记
├── .guide.md                      完整使用指南（只读）
└── sessions/                      本工作区的会话清单（机械目录）
    └── <session>/                 一个会话
        ├── RULES.md               会话规则（常驻于该会话）
        ├── notes/…                会话笔记
        └── log/                   原始记录（只读）
            ├── turns              轮次预览：轮次、时间、seq、提问与回答摘要
            ├── summaries          该会话的压缩摘要及各自覆盖的 seq 范围
            └── <seq> | <a>..<b>   事件窗口
```

当前会话是“工作目录”：`./` 等于 `/sessions/<当前会话>/`。于是：

- `./RULES.md`：当前会话规则。
- `../../RULES.md` 或 `/RULES.md`：工作区规则。
- `../<另一会话>/notes/x.md`：兄弟会话的笔记。

工作目录只决定相对路径的解析起点，不限制访问。工作区内任何位置都可读；写入只能写当前会话和工作区两个位置，并且必须在路径里写明是哪一个；工具不替模型选，选哪一个按第 3.1 节的判断。读别的会话不会改变自己的工作目录，也不会把对方的规则变成自己的规则。

### 4.3 引用

原始记录的引用直接使用 DSH 的身份，不另造记忆系统 ID：

```text
dsh://session/<session-id>               整个会话
dsh://session/<session-id>/<seq>         一个事件
dsh://session/<session-id>/<a>..<b>      一段事件
```

`<session-id>` 是 DSH 的会话 ID，通常形如 `session-<uuid>`，也有 `webhook-<uuid>`、`session-schedule-<sha256>` 等形式，插件把它当不透明字符串。`<seq>` 是该会话日志中的事件序号。DSH 的事件序号从 0 连续递增、永不复用，压缩不改变它，分叉后继承前缀中的事件在子会话里保持相同序号。消息虽然有 `MessageId`，但分叉会原样复制，跨会话不唯一，所以引用一律用“会话 ID + seq”。

- 工具输出在同一工作区内使用短 ID：去掉固定前缀后的最短唯一前缀，至少 8 个字符，类似 Git 短哈希；歧义时报错并列出候选。复制按钮和笔记 `sources` 里写完整 ID。
- `memory_view` 同时接受 DSH 现有的 `dsh-session:` 会话引用（第 10.3 节），解码后按会话处理。
- 复制按钮生成 Markdown 链接：链接文字是会话标题、轮次和时间，供人阅读；链接目标是 `dsh://` 引用，模型只按链接目标解析。用户改动或写错链接文字不影响定位，工具返回的内容以实际读到的会话为准。
- 相对路径在调用时解析成绝对引用。笔记内部的相对链接相对笔记所在位置解析，与读者的工作目录无关。
- 用户粘贴了其他工作区的完整引用时，视为用户明确授权读取这一处，只读；没有引用时不跨工作区。

### 4.4 引用指向的是事件而不是渲染位置

引用不使用压缩文件偏移、界面行号或消息在当前上下文中的位置。压缩后，被替换的事件仍按原序号可读，工具标注 `compacted (summarized in the current context)`。

### 4.5 分叉

DSH 分叉时把源会话截至分叉点的事件复制为新会话的前缀，并在切口处写入 `session/end-seed { inherited: true }`。记忆语义完全由此得出：

- 新会话的会话规则和笔记 = 源会话在分叉点的状态（因为会话记忆是日志投影，第 5.3 节）。
- 分叉之后，两边的会话记忆各自演进，互不影响。
- 工作区规则和笔记两边共享，读到的都是当前版本。

DSH 的普通分叉不在会话头里记录来源会话。插件不需要来源也能得到上述语义；来源只用于展示（“自会话 A 第 12 轮分叉”）和搜索去重。插件写进日志的每条常驻快照和提交记录都带着写入时所在的会话 ID，新会话继承前缀里的最后一条就指明了来源；前缀里没有插件记录时，用切口处事件的时间与内容指纹在同工作区内匹配。

### 4.6 子代理

子代理会话的常驻层包含工作区规则和父会话当前规则。子代理默认只读（已确认，第 14 节问题 4）：可以浏览和搜索工作区记忆与原始记录，但不能写规则和笔记；学到的经验写进交回父会话的结果里，由父会话决定是否记录。这样多个并行子代理不会各写各的，把工作区规则写乱。部署可以用配置项 `subagentWrite` 放开。

### 4.7 开关

| 开关                 | 层级               | 关闭后                                                                                       |
| -------------------- | ------------------ | -------------------------------------------------------------------------------------------- |
| 记忆总开关           | 全局、工作区、会话 | 见下表                                                                                       |
| 允许写入             | 工作区、会话       | 只读：规则照常生效，检索照常可用，模型不能写规则和笔记；常驻快照的位置说明中注明 `read-only` |
| 其他会话可检索本会话 | 会话（默认开）     | 本会话的原始记录和会话记忆不出现在其他会话的会话清单和搜索结果中；用户亲自粘贴的引用仍可读取 |
| 继承工作区记忆       | 会话（默认开）     | 干净会话：不加载工作区规则和工作区笔记索引，本会话的记忆照常工作，见下文                     |

**生效规则。** 全局是硬总闸：全局关闭时插件整体不工作，下级开关在界面上不可用。工作区和会话各有三态：跟随上级、开、关；取最近一级的明确设置，会话优先于工作区。只有会话级的开关（“其他会话可检索本会话”“继承工作区记忆”）是开、关两态。记忆总开关关闭时，其余开关在界面上不可用。

**第一个请求之前的变化不通知。** 在工作区里新开对话时，DSH 先创建一个空白会话（`packages/client/ui-workspace` 的 `createInWorkspace`），输入框绑定在这个会话上，所以会话级开关在发出第一条消息前就能设置。这时模型还什么都没看到，也没有缓存前缀需要保护，任何开关变化都直接生效、不发通知，说明和工具按第一个请求时的状态注册。下文“会话开始时”均指第一个请求。

**记忆总开关的效果。**

| 情形                                                       | 行为                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 会话开始时记忆即为关闭（来自全局、工作区或会话自身的设置） | 等效于没有安装插件：不注册使用说明和工具定义，不注入任何内容。说明和工具按会话注册在 agent 作用域，不影响其他会话                                                                                                                                                                      |
| 会话进行中关闭                                             | 追加约 40 tokens 的通知：`Memory is off for this session. Earlier memory snapshots no longer apply; do not call memory tools.` 之后不再注入，工具调用返回 `memory is off for this session`。已注册的说明和工具保留，避免中途改写系统提示和工具声明；会话下次恢复时按当时的开关状态注册 |
| 会话进行中打开                                             | 若尚未注册，追加使用说明和工具（DSH 对支持增量更新的线路只追加，其他线路在头部合并一次），随后注入完整快照                                                                                                                                                                             |
| 全局关闭                                                   | 先给运行中的会话追加关闭通知，再撤掉使用说明和工具                                                                                                                                                                                                                                     |

会话进行中的变化在下一个请求前生效，与外部修改规则的时机相同（第 14 节问题 2）。

**干净会话（“继承工作区记忆”关闭）。** 用于不想让工作区积累的规则和笔记影响这次对话的场合。

| 方面               | 行为                                                                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 常驻层             | 不注入工作区规则和工作区笔记索引；本会话的规则与笔记照常注入                                                                                                     |
| 模型               | 使用说明与工具照常注册（静态说明在所有开启记忆的会话中保持一致）；快照里的一行说明要求模型不主动读工作区笔记、不主动翻其他会话，用户明确要求或粘贴引用时照常读取 |
| 写入               | 工作区记忆只在用户明确要求时写入，写入后照常对其他会话生效；写入不会让本会话开始加载工作区记忆                                                                   |
| 会话开始时即为干净 | 快照只有位置说明和模式说明，约 40 tokens（若本会话已有自己的规则和笔记则一并列出）                                                                               |
| 会话进行中关闭继承 | 追加通知 `Workspace rules and notes no longer apply in this session. Do not consult them unless the user asks.`                                                  |
| 会话进行中恢复继承 | 注入完整快照                                                                                                                                                     |

干净会话开始时的快照：

```text
<memory-context>
Memory location: workspace "deepseek-harness" / session 9c1d07aa (clean: workspace rules and notes are not loaded)
Do not consult workspace notes or other sessions unless the user asks.
</memory-context>
```

三档“干净程度”都在输入框工具行的同一个会话控件里：正常使用是默认；不受工作区记忆影响、但本会话仍能记、能按要求查历史，关闭“继承工作区记忆”；完全没有记忆功能，关闭记忆总开关。

分叉时，会话记忆随复制的对话前缀一起继承，这一点不受开关影响；分叉后不想要，可以用记忆页的“清空本会话记忆”。

**状态存放。**

| 层级   | 存放位置                                                                      |
| ------ | ----------------------------------------------------------------------------- |
| 全局   | 插件配置字段，经 DSH 的插件设置表单修改，运行中即时生效                       |
| 工作区 | 工作区记忆目录的 `workspace.json`，改动写入修改日志                           |
| 会话   | 插件的存储域（`ctx.storageDomain`），按会话 ID 记录明确设置；“跟随上级”不记录 |

会话设置不写进会话日志：开始即关闭的会话必须等效于未安装插件，不能为了记录状态而产生模型可见的消息。中途变化时追加的通知是给模型看的，不是状态的正本。分叉出的会话复制源会话的设置，源会话按第 4.5 节的方法确定。

**关闭不等于删除。** “记忆”页另有两个需要二次确认的操作：

- 清空本会话记忆：仅在本会话记忆开启时可用，按第 5.3 节中界面修改的记录方式追加一条清空提交，下一个请求前生效。会话日志中的旧提交仍在，界面如实说明。
- 删除工作区记忆：删除工作区记忆目录，包括修改日志。原始会话记录属于 DSH，不在删除范围内，界面如实说明。

## 5 存储与正本

### 5.1 每类事实的正本

| 事实                               | 正本                              | 说明                                                               |
| ---------------------------------- | --------------------------------- | ------------------------------------------------------------------ |
| 当前代码如何实现                   | 当前代码和配置                    | 记忆只给核实入口                                                   |
| 项目开发准则                       | 仓库 `AGENTS.md` 等指导文件       | 由 `dsh-agent-instructions` 加载，记忆系统不复制                   |
| 跨工作区的个人偏好                 | `~/.dsh/AGENTS.md`                | 同样由 `dsh-agent-instructions` 在每个会话加载；记忆系统没有用户层 |
| 变更原因                           | Git 历史、决策记录、缺陷记录      | 记忆可链接                                                         |
| 用户当时说了什么、模型当时做了什么 | DSH 会话日志                      | 只读，不复制                                                       |
| 工作区规则与笔记                   | 工作区记忆文件（5.2）             | 模型和用户都可编辑                                                 |
| 会话规则与笔记                     | 该会话日志中的记忆提交事件（5.3） | 状态由日志投影得出                                                 |
| 有哪些会话、哪些轮次、哪些笔记     | 从上面各项派生的目录              | 可随时重建，不是证据                                               |

### 5.2 工作区记忆：DSH 主目录下的 Markdown 文件

```text
$DSH_HOME/memory/<WorkspaceId>/
├── RULES.md              工作区常驻规则
├── notes/                笔记，可分子目录
│   ├── README.md         （可选）本目录说明，出现在索引中
│   └── <slug>.md
├── workspace.json        最后已知的工作区路径与标题（用于接回，第 5.2 节末）
├── .journal.jsonl        只追加的修改日志（第 8.4 节）
├── .stats.json          笔记的读取次数与时间，用于健康信号（第 8.9 节）
└── .redirects.json      整理合并后的旧路径到新路径（第 8.9 节）
```

选择理由：

- **按 `WorkspaceId` 而不是路径分目录。** DSH 的 `WorkspaceId` 是生成的 UUID，工作区路径只是属性。目录移动、改名不影响记忆归属。
- **不放进仓库。** 记忆是工作区私有的工作材料，不应污染代码仓库，也不应与“仓库是项目事实正本”的定位混淆。需要团队共享的内容属于仓库 `AGENTS.md` 或文档。
- **纯 Markdown。** 人能直接打开、编辑、备份；模型对 Markdown 的读写能力最强。文件数量通常在几十到几百个，对机械硬盘也没有压力。
- **外部编辑合法。** 用户在编辑器里改了 `RULES.md`，插件在下一个请求前通过 mtime 与哈希发现，按“外部修改”处理（第 6.3 节）。
- **工作区记录被删除后重建。** DSH 删除工作区只删登记，重新添加同一目录会得到新的 `WorkspaceId`。记忆目录里保存一份 `workspace.json`（最后已知路径与标题），新工作区的路径与某个无主记忆目录匹配时，界面询问用户是否接回，不自动合并。

### 5.3 会话记忆：会话日志的投影

会话级的规则和笔记不落独立文件。每次会话级写入在该会话日志里留下一条记忆提交记录（操作、路径、内容或替换片段、结果哈希）。会话记忆的当前状态是对该会话日志从头折叠这些记录的结果，用 DSH 的 `ctx.sessionProjections` 注册一个投影单元实现，并由投影缓存加速冷读。

这样做之后，分支语义不需要额外机制：

- DSH 分叉会话时，把源会话截至分叉点的事件深拷贝为新会话的前缀。分叉点之前的记忆提交随前缀进入新会话，之后的不会。新会话的会话记忆天然等于“源会话在分叉点的状态”，之后各自演进。
- 写入是否生效与它的提交记录是否进入持久日志一致。进程在写入途中崩溃，要么日志里有这条记录，要么没有，不存在“记忆库写了但会话不知道”的中间态，也就不需要单独的候选、锚定、激活提交协议。
- 会话记忆可从日志完整重建，投影缓存丢失只影响速度。
- 读另一会话的会话记忆，就是对那个会话的日志做同样的折叠，不需要对方在线。

提交记录的载体有两种实现选择。首版用方案 A（已确认，第 14 节问题 6）：

| 方案                  | 做法                                                                                                                           | 注意                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| A：工具结果元数据     | 写入工具通过 `presentationMeta` 把提交内容放进 `tool/result.meta`，投影折叠这些结果                                            | DSH 对 PTC 模式下 `run_code` 内部的嵌套调用不生成 `meta`，需另走 `deferContext` 留下来源化消息；被工具结果裁剪器替换的结果需按 `callId` 去重 |
| B：插件自有的日志事件 | 声明一个 `ignorable: true` 的仅日志事件类型（如 `memory/commit`），写入时追加，并以同一根调用的 `tool/result` 存在作为生效条件 | 需确认外部插件声明事件类型在 DSH 格式治理下的可接受性（DSH 的 `appendPluginRecord` 目前限仓库内实验包使用）                                  |

方案 A 先覆盖默认的 `standard` 预设（原生工具执行）；PTC 预设走 `deferContext` 补充路径，单独验证。若 DSH 确认外部插件可以声明仅日志事件，再评估统一为方案 B。投影按统一的提交语义（操作、路径、内容或替换片段、结果哈希）折叠，载体只决定记录存放在哪里；将来换载体时，投影同时识别两种载体，已有会话照常读取。

用户在“记忆”页修改或清空会话记忆时没有工具调用。这类修改以一条带来源标记的通知消息追加（例如 `The user edited this session's rules in the memory panel: …`），提交内容放在消息的 `source` 元数据里，投影与工具结果一并折叠。模型反正需要知道这次修改，通知同时充当记录。会话记忆关闭时，“记忆”页只展示、不允许修改会话记忆，因此不会出现给“未安装”状态的会话追加消息的情况。

### 5.4 原始记录与机械目录

原始记录就是 DSH 会话日志：每个会话一组 `session.vN.jsonl[.zstd]` 文件，一行一个事件，压缩存储。成百上千次零碎的工具调用都在同一个日志里，不会产生零碎文件，因此不需要 VFS 或文件系统挂载。本文的“路径”只是工具解释的命名空间。

机械目录全部从正本派生：

- 会话列表：来自 `ctx.workspaceRegistry`（工作区下的 `sessionIds`）与会话标题。
- 轮次时间线：每轮的起始 seq、时间、提问预览、回答预览。DSH 已有 `session-turn-outline` 投影提供 seq 和预览（提问 50 字、回答 120 字），插件补一个带时间的同类投影即可。
- 笔记清单：扫描工作区记忆目录的 frontmatter。

DSH 自带的 SQLite 全文索引在默认组合里是关闭的（`path: ':memory:'`、`openAt: never`），且默认分词对中文子串无效（见 v0.1 第 9.3 节的实测）。首版不建全文索引（已确认，第 14 节问题 7），检索走“时间窗收窄 + 字面扫描”（第 7.3 节）。

## 6 常驻层

### 6.1 内容与预算

常驻快照由四部分组成，按顺序渲染：

1. 一行位置说明：当前工作区、当前会话（短 ID 和标题）。
2. 工作区规则：`/RULES.md` 正文。
3. 会话规则：`./RULES.md`，即当前会话日志投影出的规则。
4. 笔记索引：工作区和当前会话笔记的 frontmatter 渲染结果，每篇一行，格式为 `路径: 描述 (type)`，类型标签由 `type` 字段生成。

索引由插件从笔记 frontmatter 机械生成，不由模型另外维护一份 `INDEX.md`。描述文字是模型写笔记时自己写的，所以索引内容仍由模型决定，索引的质量也就是 description 的质量；多数请求里模型只读索引、不打开正文，description 因此按“这篇笔记最重要的那句结论”来写（第 8.2 节）。生成过程是机械的，保证“写了笔记却忘了更新索引”不会发生，也省掉每次写笔记后的第二次写入（输出 token 单价是缓存命中输入的几十倍到几百倍，第 11 节）。笔记 frontmatter 设 `index: false` 可以不进索引；目录级 `README.md` 的描述提供人工归类说明。这是已确认的决策（第 14 节问题 3），与 Claude Code 由模型维护 `MEMORY.md` 的做法不同。

预算起始值：规则每个作用域 1,600 tokens，索引 1,600 tokens，合计上限约 5K tokens，均可配置，实现后按实测调整。作为参照，DSH 默认组合下只发一句“hi”的请求就有约 8,960 tokens（用户实测）；常驻层与之同量级，而且只在会话首个请求和每次压缩后按未命中计价，其余请求都是缓存命中价。

- 规则超预算时，写入工具拒绝提交并返回当前用量和上限，由模型合并、缩短，或把非持续性内容移到笔记。不截断，不按时间淘汰。
- 索引超预算时折叠，不静默丢条目。折叠按以下顺序进行，每一步后重新计算，回到预算内就停：
  1. 按子目录折叠：篇数最多的子目录先折叠，篇数相同按路径排序。一个子目录折成一行，写篇数和该目录 `README.md` 的描述。
  2. 子目录全部折叠后仍超预算，把直接放在 `/notes/` 下的笔记按类型合成一行，写各类型的篇数。
  3. 仍超预算（目录本身过多），只保留目录行，末尾写明还有多少个目录未列出。

  折叠后的索引标题写明已折叠，模型用 `memory_view` 读目录即可展开：

```text
## Note index (folded; memory_view a directory to expand)
- /notes/build/: 12 notes. 构建、交叉编译与签名
- /notes/decisions/: 15 notes. 各次方案讨论的结论
- /notes/*.md: 23 lesson, 9 decision, 4 context
```

目录行只能写主题，被折叠笔记的结论不再常驻，模型要先读目录才看得到。所以开始折叠本身是一个健康信号（第 8.9 节）。

### 6.2 组合与优先级

从高到低：

| 优先级 | 来源                                                    | 由谁加载                 |
| ------ | ------------------------------------------------------- | ------------------------ |
| 1      | 宿主系统与开发者约束、用户在当前对话中的直接指令        | 宿主                     |
| 2      | 仓库指导文件（`AGENTS.md`、`CLAUDE.md` 及其子目录版本） | `dsh-agent-instructions` |
| 3      | 当前会话规则                                            | 本插件                   |
| 4      | 工作区规则                                              | 本插件                   |

笔记、索引、搜索片段和原始历史都不是指令层。历史里的“以后都这样做”只说明用户当时说过这句话，只有被写进规则的内容才是当前要求。

仓库指导文件高于记忆规则，因为它经过评审、有版本、与团队共享，而记忆规则是模型写的。会话规则高于工作区规则，因为它更具体。

继承默认叠加：会话规则加在工作区规则之上，创建会话规则不会让工作区规则消失。会话规则可以用自然语言写明例外（“本会话内不适用工作区规则中关于回归测试的一条”）。需要整个会话不受工作区记忆影响时，由用户关闭会话级开关“继承工作区记忆”（第 4.7 节）；规则文件本身不提供停止继承的标记，避免文件与开关两处表达同一件事。默认叠加是已确认的决策（第 14 节问题 1）：规则文件由模型写，若采用“有本级文件就不继承”，模型写一条会话规则就会让全部工作区规则在该会话悄悄失效。

`RULES.md` 中单独成行的 `@notes/<slug>.md` 把该笔记正文并入常驻规则，计入预算，只展开一层。笔记正文和历史原文中的 `@` 文本不展开。

### 6.3 何时注入

以下只适用于记忆总开关对本会话生效为开的情形；关闭时的行为见第 4.7 节。

插件不记录“上次发了什么”的私有状态，而是每个请求前比对两样东西：

- **模型此刻看得到的版本**：会话可见上下文里仍然存在的本插件快照与增量消息，加上仍然可见的本会话记忆写入工具结果。
- **当前实际版本**：现在组合出的常驻快照。

| 情形                                                                       | 动作                                                     | 增量成本                   |
| -------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------- |
| 看不到任何快照（会话首个请求；压缩把快照替换掉了；恢复的会话快照已被压缩） | 注入完整快照                                             | 一次，约 0.5K 至 5K tokens |
| 两者一致                                                                   | 不注入                                                   | 0                          |
| 差异来自本会话自己的写入，且写入结果仍可见                                 | 不注入。模型刚写过，上下文里有工具调用和结果             | 0                          |
| 差异来自外部（其他会话、用户手改文件）                                     | 规则变化注入增量通知；仅索引变化不注入，留到下次完整注入 | 约 50 至 150 tokens        |
| 差异超过预算的一半                                                         | 注入完整快照代替增量                                     | 同首次                     |

比对用结构化数据而不是比较文本。每条注入消息的 `source` 元数据里带上它所表达的状态：各作用域规则的内容哈希、索引哈希、当前会话 ID；增量通知带它改变的部分。模型看到的正文不含这些隐藏标记，符合 DSH 对注入消息的约定。算法：

```text
believed = 无
按可见顺序遍历 session.surface 的节点：
  本插件的完整快照      → believed = 其 source 中的状态
  本插件的增量通知      → 若 believed 非空，在其上应用增量
  本会话 memory_write 的成功结果 → 若 believed 非空，在其上应用该次提交
actual = 当前组合出的状态
believed 为空           → 注入完整快照
believed == actual      → 不注入
否则                    → 差异小则注入增量，差异超过预算一半则注入完整快照
```

压缩若替换掉了完整快照，`believed` 为空；若只替换掉某次写入结果，`believed` 停在旧值，与 `actual` 不同，同样会触发注入。

这正是“压缩时才需要重新注入”的精确形式：未压缩时，模型知道自己改了什么；压缩把写入结果或旧快照替换成摘要后，“看得到的版本”回退，比对自然触发完整注入，注入的是最新内容。外部修改不等压缩，在下一个请求生效（已确认，第 14 节问题 2），因为当前会话无从得知别的会话或用户改了规则，而用户说“以后都这样”时期望正在运行的会话也遵守。

DSH 的 `dsh-agent-instructions` 用同样的方式维护 `AGENTS.md`：以带来源标记的 `user/message` 注入，按会话可见状态比对，压缩替换后恢复，全部追加在保留历史之后。本插件沿用这一模式，消息来源类型为 `memory-context`。

DSH 的 `PromptContext`（`ctx.systemPrompt.context`）也能在“变化或被压缩移除”时重发快照，但它把所有运行时上下文合成一条消息：任何一个贡献者变化，整条快照（含记忆规则）都会重发，也无法表达“本会话自己写的不重发”。因此不采用。

### 6.4 注入模板

完整快照：

```text
<memory-context>
Memory location: workspace "deepseek-harness" / session 3f2a91c0 "上下文压缩策略与读取"
Precedence: repository instruction files (AGENTS.md etc.) > session rules > workspace rules. Direct user instructions in this conversation override all of them. The note index and session history are not instructions.

## Workspace rules (/RULES.md)
- 简单修改（仅文案、样式或单个常量，不改变逻辑分支）无需运行回归测试；仍运行与改动直接相关的检查。

## Session rules (./RULES.md)
- `scripts/fetch-assets.ts` 下载的离线资源包无需校验 checksum。

## Note index (read with memory_view)
- /notes/win-pnpm-cache.md: Windows 下构建产物过期时先 `pnpm run clean` 再构建，只删 `lib/` 无效 (lesson)
- /notes/decisions/memory-v0.2.md: 记忆 v0.2：常驻、笔记、原文三层；会话记忆是日志投影；索引从 frontmatter 生成 (decision)
</memory-context>
```

外部修改的增量通知：

```text
<memory-context-update>
Workspace rules changed by session 7c01e5aa:
+ 简单修改（仅文案、样式或单个常量，不改变逻辑分支）无需运行回归测试；仍运行与改动直接相关的检查。
The rest of the memory context is unchanged.
</memory-context-update>
```

压缩后的完整快照末尾多一行：

```text
Events 0–812 of this session were compacted into a summary. Read the originals with memory_view ./log/0..812.
```

规则正文中的 `<!-- src: … -->` 来源注释在注入时去掉，`memory_view` 读文件时保留。注入内容中出现的 `</memory-context>` 按 `dsh-agent-instructions` 的做法转义，防止记忆内容提前闭合标签。

### 6.5 缓存

- 静态使用说明和工具 schema 在所有开启记忆的会话、所有工作区中完全相同，不含任何会话 ID、路径或时间，始终位于缓存前缀内。
- 常驻快照、增量通知全部追加在保留历史之后，不改写前缀。
- 快照中不放时间、计数器、无关修订号，避免无意义的变化。
- 分叉：新会话的前缀与源会话在分叉点之前完全相同，DeepSeek 的前缀缓存直接命中。新会话的第一个请求比对时，“看得到的版本”是继承来的源会话快照，通常只差位置说明一行，于是只追加一条约 40 tokens 的位置变更通知，不重发整份快照：

```text
<memory-context-update>
Memory location is now session 9b77d2e1 (forked from session 3f2a91c0 at turn 12). Session rules and notes start from their state at the fork point and evolve independently of the source session.
</memory-context-update>
```

## 7 检索

### 7.1 检索阶梯

模型需要上下文里没有的历史时，按成本从低到高尝试，哪一步拿到足够依据就停：

| 步骤 | 做法                                                                     | 典型成本                             |
| ---- | ------------------------------------------------------------------------ | ------------------------------------ |
| 0    | 上下文里已有，直接用                                                     | 0                                    |
| 1    | 用户粘贴了引用（第 10.3 节的“复制引用”按钮），直接读该位置前后的事件窗口 | 1 次调用，约 1K 至 3K tokens         |
| 2    | 常驻索引中有相关笔记：读笔记；需要原文时跟随笔记里的来源引用             | 1 至 2 次调用，约 0.5K 至 3K tokens  |
| 3    | 浏览机械目录：按时间窗列出会话与轮次预览，选中后读事件窗口               | 2 至 3 次调用，每轮预览约 50 tokens  |
| 4    | 读候选会话的压缩摘要：长会话压缩过时，摘要里有“决策及其理由”一节         | 1 至 2 次调用，约 1K 至 4K tokens    |
| 5    | 搜索：限定会话或时间窗做字面匹配，返回片段和引用                         | 1 至 3 次调用，约 1K 至 2K tokens/次 |
| 6    | 问用户                                                                   | 1 轮对话                             |

第 2 步优先于搜索：索引是模型自己写的高信噪比入口，读一篇笔记通常比读几页搜索片段便宜。第 3 步优先于第 4 步：用户的描述里往往有时间（“昨晚”“上周五”），按时间列轮次预览比全文搜索更便宜，而且不受中文分词影响。第 4 步也排在搜索之前：DSH 的压缩指令要求摘要单列“决策及其理由、约束、用户偏好、未决问题”，长会话一旦压缩过，日志里就有一份现成的决策摘要，生成费用早已付过。它的局限是只覆盖压缩过的部分，最后一次压缩之后的讨论不在其中；摘要是英文、有损的，按时间段而不是话题组织，用它定位之后仍应读原文核实。

其他会话的会话笔记不在本会话的索引里，在第 3 步和第 5 步中出现：会话清单每行显示该会话的规则条数与笔记篇数，在 `/sessions` 下搜索时包括会话笔记（第 8.5 节）。

**何时直接问用户。** 用户的描述缺少可定位的锚点（时间、关键词、文件名、会话名都没有），第 2 至 4 步也没有候选时，不做大范围搜索，直接问一个具体问题。候选多于三个且无法区分时，把候选列给用户选。问法示例：“你指的是 11 月 9 日 23:10 左右『记忆系统设计』会话里关于分层的讨论，还是 11 月 10 日下午关于缓存的那次？”DSH 的 `ask_user_question` 工具可以把候选做成结构化选项。

### 7.2 例：找回“昨晚讨论的方案”

用户在新会话说：“首先，昨天晚上十一点左右我和你讨论的那个记忆分层方案，按那个思路继续。”

1. DSH 的 `dsh-time-context` 给出当前时间和用户时区，模型把“昨晚十一点左右”换算成一个较宽的窗口，例如 21:30 至次日 01:00。
2. 常驻索引里没有相关笔记（昨晚没人写），跳到第 3 步：`memory_view`（`path=/sessions`，带 `since`、`until`）列出该窗口内有活动的会话，每个会话一行。
3. 选中标题最接近的会话，`memory_view`（`path=/sessions/3f2a91c0/log/turns`，带 `since`）列出窗口内的轮次预览。
4. 预览里看到“第 14 轮 23:05：分三层……”，读 `/sessions/3f2a91c0/log/1520..1610` 一段原文，区分提议、反对和最终结论。若后面还有修订，继续往后读。
5. 用找到的原文接着工作，并说明依据的位置。这次是从原文找回的，按第 8.6 节补写一条决策指针，下次找回只需一次读取。

全程约 4 次调用、3K 至 6K tokens 的新增输入。若第 2 步命中决策指针，则降到 1 至 2 次调用。

### 7.3 搜索语义

- 默认字面匹配：大小写不敏感、空白宽松，对中文子串有效。底层用 DSH `ctx.sessionQuery.filterEvents` 的 `text` 条件，它扫描事件的语义文本，不依赖全文索引。
- 必须先收窄范围：搜索必须给出路径前缀（某个会话、`/notes`）或时间窗。路径前缀为 `/sessions` 或某个会话时，范围包括原始记录和会话笔记，结果按来源分组。工作区全量扫描只在模型显式要求时进行，结果说明扫描了多少会话。
- 结果给出每条命中的引用、角色、时间和约 80 字片段，按时间排序，带“已扫描范围”和“是否截断”。
- 零结果要说明查询方式和范围，模型据此改用同义词、扩大时间窗或问用户。零结果不等于“用户没说过”。检索失败、目标会话不可读和真正无匹配返回不同的状态。
- 分叉会话的继承前缀与源会话内容相同，跨会话搜索按事件时间与内容指纹去重，只报告最早的出处并注明 `also in forked session <id>`。
- 当前会话已被压缩的部分同样可搜可读，范围写 `./log`。

首版不建全文索引。是否在第二阶段加入（例如 SQLite FTS5 的 trigram 分词），以第 10.5 节第 5 项的实测为依据：字面扫描在目标硬件上对一个工作区一周的会话量耗时过长时再加。trigram 对两个字的中文词仍然无效，加入时仍需保留字面扫描作为回退。

## 8 写入与整理

### 8.1 规则文件格式

`RULES.md` 是一个简短的列表，每条一到两行，写清条件和要求。来源用 HTML 注释附在行尾，注入时去掉。

```markdown
- 简单修改（仅文案、样式或单个常量，不改变逻辑分支）无需运行回归测试；仍运行与改动直接相关的检查。<!-- src: dsh://session/session-7c01e5aa-…/1203 -->
- 回复使用中文；代码标识符、命令和报错保持原文。
```

规则不编号、不设规则 ID、不设计规则语言。覆盖和例外用自然语言表达，冲突由模型阅读来源后判断，同层冲突且无法判断时问用户。

### 8.2 笔记格式

笔记是带 frontmatter 的 Markdown。字段取 OKF 与 Claude Code 记忆格式的交集再做裁剪：

```markdown
---
description: Windows 下构建产物过期时先 `pnpm run clean` 再构建，只删 `lib/` 无效
type: lesson # lesson | decision | context | reference
status: active # active | superseded | archived
sources:
  - dsh://session/session-3f2a91c0-…/2210..2236
verified: 2026-11-10 @ fcc0ad4621 # 可选：最后核实的日期与提交
---

条件：Windows，`pnpm run build:artifacts` 后 `lib/` 时间戳更新但内容是旧的。
现象：……
做法：先 `pnpm run clean`，再构建；不要只删 `lib/`。
证据：见 sources 中的命令输出（seq 2231）。
未验证：是否与杀毒软件的文件锁有关。
```

| 字段          | 必填                      | 用途                                                                                                                             |
| ------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `description` | 是                        | 索引中的那一行，一句话，建议 40 字左右。写这篇笔记最重要的那句结论，写法见表后；类型、状态、日期、来源由各自字段渲染，不写进描述 |
| `type`        | 是                        | `lesson` 经验，`decision` 决策指针，`context` 无法从仓库得到的背景，`reference` 外部资料指针                                     |
| `status`      | 否，默认 `active`         | `superseded` 时正文首行写明被哪篇取代                                                                                            |
| `sources`     | `lesson`、`decision` 必填 | 指向原始记录或仓库文件的引用                                                                                                     |
| `verified`    | 否                        | 涉及仓库实现时，写最后核实的提交，供使用前判断是否过时                                                                           |
| `index`       | 否，默认 `true`           | `false` 时不进常驻索引                                                                                                           |

**`description` 写结论，不写主题。** 索引每个请求都在上下文里，正文只在模型判断相关时才打开，所以多数时候模型只看得到 description，判断相关和照着做都靠这一句（第 14 节问题 15）。它应当是整篇笔记最重要的那句话：只读这一行、不打开正文，模型就知道该怎么做，也能判断正文值不值得打开。

| 类型        | 写什么                   | 好                                                                           | 差                                   |
| ----------- | ------------------------ | ---------------------------------------------------------------------------- | ------------------------------------ |
| `lesson`    | 条件和做法               | Windows 下构建产物过期时先 `pnpm run clean` 再构建，只删 `lib/` 无效         | Windows 下 pnpm 缓存问题的识别与处理 |
| `decision`  | 结论本身                 | 记忆 v0.2：常驻、笔记、原文三层；会话记忆是日志投影；索引从 frontmatter 生成 | 记忆系统 v0.2 讨论结论               |
| `context`   | 事实及其直接影响         | 演示环境数据库每晚 3 点重置，测试数据不能跨天保留                            | 演示环境数据库说明                   |
| `reference` | 资料回答什么问题、在哪里 | DeepSeek 缓存的计价与前缀匹配规则：api-docs.deepseek.com/guides/kv_cache     | DeepSeek 缓存文档                    |

一句话装不下时，先删修饰，保留条件和限定词。“Windows 下”“只删 `lib/` 无效”这类边界正是照做时最容易出错的地方，与规则保留边界词（第 3.1 节）是同一个道理。具体例子、理由、证据和次要的适用边界放正文。

**一篇笔记只记一个事实。** 一句 description 只能代表一个事实。正文里长出第二条独立的结论，它在索引里就不存在，只有恰好打开这篇的模型才看得到，应当拆成单独的笔记。判断标准：它能不能脱离前一条单独成立、单独被用到。同一结论的条件、例外、理由和证据属于同一个事实，留在一篇里。删掉修饰后仍装不下一句，通常也说明这篇记了不止一件事。

决策指针示例，故意很短：

```markdown
---
description: 记忆 v0.2：常驻、笔记、原文三层；会话记忆是日志投影；索引从 frontmatter 生成
type: decision
sources:
  - dsh://session/session-3f2a91c0-…/1520..1610
---

结论：……三到五行……
未决：要不要路径作用域的规则。
```

### 8.3 操作与并发

| 操作      | 语义                                                               |
| --------- | ------------------------------------------------------------------ |
| `create`  | 新建文件；已存在则失败                                             |
| `append`  | 在文件末尾追加内容，最常用于新增一条规则                           |
| `edit`    | 精确替换一段文本（与 `str_replace` 相同），旧文本必须唯一匹配      |
| `replace` | 整体覆盖文件内容；返回结果列出被删除的行，让模型看见自己丢掉了什么 |
| `archive` | 把笔记 `status` 改为 `archived`，退出索引，文件保留                |
| `delete`  | 删除笔记文件；修改日志保留这次删除                                 |

`replace` 返回被删除的行，是因为 Hermes 的经验：模型曾把整体替换当作查找替换使用，抹掉了同一条目里的其他事实，Hermes 因此去掉了 `replace`。本设计保留它用于合并整理，但让副作用可见。

并发控制沿用代码编辑工具“先读后改”的规则：`edit` 和 `replace` 要求当前会话读过该文件，且文件从那次读取以来没有变化（按内容哈希判断）。别的会话或用户在此期间改过文件，写入失败并提示重新读取。`edit` 的旧文本匹配本身也会挡住大部分冲突。程序不做自然语言合并，也不做“后写覆盖”。

同进程内的写入按工作区串行。DSH 桌面版与 npm CLI 共用 `$DSH_HOME` 下的产品数据，可能同时运行，因此“比对哈希、原子写入、追加日志”这一段在工作区目录的锁文件（排他创建）保护下执行，跨进程也不会交错。读取不加锁。

### 8.4 修改日志

工作区记忆目录下的 `.journal.jsonl` 是只追加的修改日志。每次写入追加一行：时间、写入者（会话 ID 与调用 ID；外部编辑记为 `external`）、路径、操作、新内容哈希和新内容全文（删除时为空）。插件在请求前发现外部编辑时，同样追加一行。

记忆文件本身是当前状态，日志是它的历史，两者分工不重叠。用途：

- 审计“这条规则是谁、在哪次对话里写的”，并跳回那次对话。
- 还原任意旧版本，包括被外部编辑覆盖之前的版本。
- 记忆文件损坏或被误删时，从日志重建当前状态。

记忆文件很小，日志增长有限（1,000 次写入、每次 2 KB 约 2 MB）。日志只有一个文件，不按版本拆小文件。

### 8.5 作用域之间的移动

- 会话经验提升到工作区：读会话笔记，在 `/notes/` 下新建，`sources` 引用原会话笔记或原始记录；需要时把会话笔记归档。两者不建立同步关系。
- 读取别的会话的规则或笔记，不会改变当前会话的规则；要采用规则，就在当前作用域写一份并注明来源。

会话笔记不进入其他会话的索引，有价值的内容可能因此留在会话里。三处补救：

1. **写入提示。** 写入 `./notes/` 时，结果附一句 `Visible only to this session and sessions forked from it later. If it holds beyond this session, write it under /notes/ instead.`，约 25 tokens，只在会话级写入时出现，正好在做决定的时刻。
2. **跨会话可发现。** 会话清单 `/sessions` 的每一行显示该会话的规则条数与笔记篇数；在 `/sessions` 下搜索时，范围包括会话笔记，不只是原始记录。
3. **用过就提升。** 某个会话从另一会话的会话笔记里拿到了有用的内容，就把它复制成工作区笔记，`sources` 指回原处；原笔记属于别的会话，不改动。跨会话真被用到，说明它有跨会话的价值。这与“找回时补写”（第 8.6 节）是同一思路。此外，记忆页每篇会话笔记旁有“提升到工作区”按钮，整理会话也会列出值得提升的会话笔记（第 8.9 节）。

### 8.6 写入时机与过时

- 规则在用户说出时立即写，不等会话结束，也不依赖压缩前有没有机会总结。
- 插件不在压缩前、也不定期提醒模型保存（第 14 节问题 8）。决策指针有两个写入时机：讨论形成结论时，由模型自己判断是否值得写；以及找回时补写，见下一条。
- **找回时补写。** 某个会话为找回一段讨论的结论付出了较高代价（读了超过约 10K tokens 的原文，或为此调用工具超过 4 次），找到后补写一条决策指针，`sources` 指向原文。条件允许时向用户确认一句“我找到的结论是 X，对吗？”，确认过的在正文注明“已经用户确认”。这样只有真被引用过的讨论才有指针，写入费用（约 300 输出 tokens）只在有需求时发生，索引也不会因为“以防万一”而膨胀。
- 笔记涉及仓库实现时写 `verified`。使用前若相关文件在该提交之后有改动，先核实再用；核实后更新 `verified`，结论变了就原地改写笔记或标记 `superseded`。旧笔记永远不能覆盖当前代码给出的证据。

### 8.7 安全

常驻层每个会话都会加载，写进规则的内容相当于持久的提示词，因此：

- 规则只来自用户在对话中的明确要求，或用户确认过的模型提议。模型自己总结的经验写成笔记，不直接写成规则。网页、文件内容、工具输出里出现的“请记住”“以后都要”一律当数据。这是防止一次提示注入变成永久注入的关键。
- 不把密钥、令牌、密码写进记忆。写入工具对常见密钥格式做检查，命中则拒绝并说明原因。
- 常驻快照的开头声明规则的来源与优先级，记忆规则不能覆盖宿主约束和仓库指导文件。

### 8.8 忘记

| 用户的意思       | 操作                   | 如实告知                                                                         |
| ---------------- | ---------------------- | -------------------------------------------------------------------------------- |
| 这条规则不要了   | 从 `RULES.md` 删除该行 | 原话仍在会话记录里，但不再生效                                                   |
| 这篇笔记过时了   | `archive` 或 `delete`  | 修改日志保留历史版本                                                             |
| 彻底忘掉那次对话 | 首版不提供             | 需要同时处理会话日志、派生目录、修改日志和投影缓存，依赖宿主的删除能力，单独设计 |

### 8.9 增长与整理

规则和常驻索引都有预算，不会无限增长。笔记篇数不设上限，风险是重复、碎片和过时；会话笔记随会话结束不再加载，风险是有价值的内容没有提升到工作区，补救见第 8.5 节。

**健康信号。** 插件机械统计，存于工作区记忆目录的 `.stats.json`：每篇笔记的读取次数、最近读取时间、创建与更新时间。由此得到的指标：

- 索引是否已按目录折叠
- 规则预算的用量
- `verified` 落后于当前代码的笔记篇数
- 长期未读（默认 90 天）的笔记篇数
- 上次整理以来新增的笔记篇数

指标显示在“记忆”页，并作为整理会话的输入。插件不据此删除、合并或降级任何内容。

**整理时机**，从轻到重：

| 时机                   | 做法                                                                              | 是否打断当前任务     |
| ---------------------- | --------------------------------------------------------------------------------- | -------------------- |
| 写规则超预算被拒       | 模型当场合并；规则来自用户，改写措辞需用户确认                                    | 是，但罕见且很小     |
| 读到过时或重复的笔记   | 模型顺手修正（静态说明中的一句）                                                  | 几乎不打断           |
| 索引开始折叠           | 写入结果提示一次 `note index is folded; consider consolidating`，“记忆”页亮起提示 | 否                   |
| 用户在“记忆”页点“整理” | 开一个整理会话                                                                    | 否，在独立会话中进行 |

不做定期自动整理：费用与实际需求不对齐，改动也会发生在用户不知情的时候。

**整理会话。** 一个普通的 DSH 会话，带整理指南（`/.guide.md` 的整理一节），可以选用更便宜的模型。

1. 读全部笔记和健康信号，给出整理计划：合并、拆分记了不止一个事实的笔记、把只写主题或与正文结论不符的描述改写成结论、归档、调整目录、建议提升到工作区的会话笔记。
2. 用户审阅计划，确认一次后执行；涉及规则的改动逐条确认。
3. 全部过程记录在该会话日志中；修改日志按这次整理会话分组，可以整体回滚。

估算：100 篇、每篇约 400 tokens 时，约 40K 输入、5K 至 10K 输出，一次整理用 Flash 约 $0.01，用 Pro 约 $0.05。

**整理的保证。**

- 只合并陈述同一事实的笔记，合并后的 description 仍是一句结论（第 8.2 节）。`sources` 取被合并笔记来源的并集。旧路径写入 `.redirects.json` 后删除旧文件；`memory_view` 读到旧路径时自动跳到新路径，并注明合并去向。
- 拆分时，原路径留给主要的那个事实，其余事实各写一篇新笔记，`sources` 沿用原笔记中支撑它的来源。原路径仍然有效，不需要重定向。
- 归档的笔记退出索引，文件保留。
- 不丢来源，不把推测写成已确认，不在用户未确认时改变规则的含义。

**整理后的上下文刷新。**

| 改动         | 其他正在运行的会话                                                                           |
| ------------ | -------------------------------------------------------------------------------------------- |
| 规则         | 属于外部修改，下一个请求生效（第 14 节问题 2）；改动多时注入一次完整快照                     |
| 仅笔记与索引 | 不立即注入。旧索引里的路径经重定向仍可用，新索引在下次完整注入时出现，即压缩后或新会话开始时 |

整理会话自己看得到全部修改。

## 9 工具面

两个工具。读工具只读、可并行；写工具串行。名称、字段和措辞是插件拟定的接口，实现时测量 schema 长度后定稿。

### 9.1 `memory_view`

| 参数             | 说明                                                                                                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`           | 必填。命名空间路径（第 4.2 节）或 `dsh://` 引用。文件返回内容，目录返回清单，`log/turns` 返回轮次预览，`log/summaries` 返回压缩摘要及覆盖范围，`log/<seq>` 或 `log/<a>..<b>` 返回事件窗口 |
| `query`          | 可选。给出时改为在 `path` 之下做字面搜索                                                                                                                                                  |
| `since`、`until` | 可选。带时区的 ISO 8601 时间，用于会话清单、轮次预览和搜索                                                                                                                                |
| `detail`         | 可选，`brief`（默认）或 `full`。`brief` 折叠长工具输出、省略推理内容；`full` 返回完整事件                                                                                                 |
| `cursor`         | 可选。上一次结果给出的续读标识                                                                                                                                                            |

返回格式以紧凑文本为主，不返回 JSON 外壳。示例（`>` 行是调用的简写）：

```text
> memory_view /sessions since=2026-11-09T21:30+08:00 until=2026-11-10T01:00+08:00
Sessions in workspace "deepseek-harness" active in this window (2):
3f2a91c0 "记忆系统设计" 11-09 21:40–23:55 · turns 9–17 · 1 rule, 2 notes
7c01e5aa "Go 交叉编译" 11-09 22:10–22:30 · turns 3–4

> memory_view /sessions/3f2a91c0/log/turns since=2026-11-09T22:30+08:00
#14 23:05 seq1520 Q: 我想把记忆分成三层，常驻、笔记、原文…… A: 建议常驻层只放规则和索引……
#15 23:31 seq1611 Q: 那分支以后会话记忆怎么继承…… A: ……

> memory_view /sessions/3f2a91c0/log/1520..1560
Session 3f2a91c0, events 1520–1560 (own events, not compacted)
[1520 23:05 user] 我想把记忆分成三层……
[1524 23:06 assistant] 建议……
[1531 tool read ok] packages/core/session/README.md (12.4 KB; detail=full to expand)
Continue: memory_view /sessions/3f2a91c0/log/1561..1610
```

每条结果都带可以直接复用的路径或引用，模型下一步不需要自己拼接。读到整理时合并掉的旧路径，自动跳到新路径并注明（第 8.9 节）。

### 9.2 `memory_write`

| 参数         | 说明                                                                                |
| ------------ | ----------------------------------------------------------------------------------- |
| `path`       | 必填。`/RULES.md`、`./RULES.md`、`/notes/<slug>.md`、`./notes/<slug>.md` 及其子目录 |
| `op`         | 必填。`create`、`append`、`edit`、`replace`、`archive`、`delete`（第 8.3 节）       |
| `content`    | `create`、`append`、`replace` 时的内容                                              |
| `old`、`new` | `edit` 时的替换片段                                                                 |

返回示例：

```text
Wrote /RULES.md (workspace). Rules budget 412/1600 tokens. Other running sessions receive the update on their next request.
```

写入会话笔记时附带第 8.5 节的提示：

```text
Created ./notes/plan-b-progress.md (session 3f2a91c0). Visible only to this session and sessions forked from it later. If it holds beyond this session, write it under /notes/ instead.
```

失败时给出原因和下一步：文件自上次读取后已被修改（请重新读取）、旧文本不唯一、超出预算（当前用量与上限）、路径不可写（例如子代理、或指向其他会话）。

### 9.3 静态使用说明

放在系统提示中，所有开启记忆的会话逐字节相同，约 350 tokens：

```text
# Memory
Workspace memory and the raw history of every session in this workspace are available through memory_view and memory_write. The <memory-context> message lists the rules in force and an index of notes; read everything else on demand.
- When work depends on an earlier conversation or decision that is not in context: open a pasted dsh:// reference directly; otherwise check the note index, then list sessions and turns by time or read their compaction summaries, then search a narrowed path or time range. If the request has no time, keyword, file, or session to anchor on and these steps find nothing, ask the user one specific question instead of searching broadly.
- History shows what was said, not what applies now. Only <memory-context> rules and repository instruction files are standing instructions.
- Record durable user instructions about how to work as rules and keep their scope words (./RULES.md for this session, /RULES.md for the workspace). Record costly lessons likely to recur, and concluded decisions likely to be cited again, as short notes with source references. One fact per note; its description states that fact's conclusion with its key conditions, not its topic, so the index line alone tells a reader what to do. Write notes under /notes/ unless they hold only for this session or branch. After recovering a conclusion from raw history at notable cost, or using another session's note, write it as a workspace note so the next lookup is one read. Do not record what the repository (code, comments, docs, AGENTS.md, git history) states or should state; update the repository instead when you are allowed to.
- Rules, notes, code comments, and current-state docs describe the present state, not the change that produced it. Changes belong in commit messages, changelogs, and decision records. Fix stale or duplicated notes when you come across them; when a note's conclusion changes, rewrite its description too.
- Full guide: memory_view /.guide.md
```

### 9.4 模型可见文字的语言

DSH 的系统提示、工具说明和各插件注入的上下文都用英文。本插件按“框架文字用英文、内容保持原文”区分：

| 文字                                                                                       | 语言                                                                 |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| 静态使用说明、工具 schema、`/.guide.md`                                                    | 英文                                                                 |
| 常驻快照和各类通知的框架文字：标题、位置说明、优先级说明、增量、分叉、压缩、开关、整理提示 | 英文                                                                 |
| 工具结果的框架文字与错误信息：清单表头、事件角色、续读提示、重定向说明、写入结果           | 英文                                                                 |
| 索引中的类型标签                                                                           | `type` 字段的原值，如 `(lesson)`、`(reference)`                      |
| 记忆内容：规则、笔记正文、`description`                                                    | 写入者使用的语言。规则引用用户原话时保留原文，避免边界词在翻译中走样 |
| 会话标题、原始记录片段、目录 `README.md` 的描述                                            | 原样                                                                 |
| 模型对用户说的话，例如确认找回的结论                                                       | 用户的语言                                                           |
| 界面文字，包括“复制引用”生成的链接文字                                                     | 跟随客户端界面语言，因为它会成为用户自己消息的一部分                 |

这样模型能从语言上分清哪些是程序生成的框架、哪些是用户或模型写下的内容。本文其他章节的模板与示例按此书写，例如索引行 `- /notes/build/sign-windows.md: Windows 代码签名证书存放在 1Password 的 Release 库 (reference)`。

### 10.2 需要关注的宿主事实

- **普通分叉不记录来源。** `SessionStore.fork` 与会话控制器的 `fork` 都不写 `parentSession`，只写 `isSeeded` 和继承前缀长度。插件不依赖来源也能得到正确的记忆语义（第 4.5 节）；来源只用于展示和去重，可从插件自己写进前缀的消息中得到。若 DSH 将来在分叉时记录来源，插件改用宿主数据。
- **会话 ID 形如 `session-<uuid>`，事件以 `seq` 定位。** 分叉时继承前缀的事件被深拷贝，子会话中前缀事件的 `seq` 与源会话相同。
- **默认组合中全文索引关闭。** 见第 5.4 节。
- **现有 `dsh-tool-session-query` 以 `cwd` 字符串完全相等判定可跨会话访问。** 本插件以 `WorkspaceId` 的 `sessionIds` 判定，路径变化和符号链接不影响归属。两者可以共存，但同时启用会让模型看到两套历史工具，建议本插件启用时关闭它。
- **PTC 预设。** `run_code` 内部的嵌套工具调用没有独立的 `tool/result.meta`，会话记忆提交记录需要第 5.3 节的补充路径。
- **子代理会话**（`origin: 'subagent'`）通过会话谱系找到所属工作区，控制器的 `forkWorkspace` 已有同样的查找。
- **Git worktree 不拆分工作区。** DSH 的 worktree 功能通过工作目录服务进入新检出目录，不改变会话头里的原始项目目录，因此会话仍属于原工作区，记忆照常共享。Claude Code 按 Git 仓库归属记忆以覆盖 worktree，DSH 下按工作区归属已经达到同样效果。
- **压缩摘要不保留引用。** `dsh-compaction-basic` 的摘要指令是固定文本，摘要里通常不会留下 seq。插件靠压缩后快照末尾的“已压缩范围”一行补上回到原文的入口。若 DSH 将来允许插件向摘要指令追加要求（类似 Claude Code 的 `PreCompact` 钩子输出会成为摘要指令），可以要求摘要保留关键 `dsh://` 引用。

### 10.3 界面入口

外部插件可以带客户端界面。包的 `package.json` 声明 `dsh.client`（`platform: 'web'`）并导出 `./client`，随包提供构建好的 `lib/client.js`；Host 面可以是空的 `apply`，在 bundle 的 `cordis.patch.yml` 里登记一行。`ctx.clientModules` 扫描这些条目并在页面启动时加载。安装走 `dsh plugin add`、插件页的“安装第三方插件”或插件市场，都经过 `pluginManager.installBundle`。客户端代码没有沙箱，也不签名，Host 代码在进程内以完整权限运行。参照：`packages/client/ui-message-feedback`（点赞点踩就是这样一个插件）、`docs/subsystems/client-modules.md`。

**消息操作栏的“复制引用”按钮。**

- 扩展点是列表槽位 `conversation.chat.assistant-actions`（会话作用域，owner 为 `{ messageId }`），定义在 `packages/client/ui-chat/src/client/contract/slots.ts`。插件按钮排在复制之后、分叉之前。点赞点踩的注册方式（`packages/client/ui-message-feedback/src/client/index.ts`）可以照抄。
- 这一行每轮只有一个，挂在该轮最后一条完成的助手消息下，不是每个助手步骤一个。被中断的半截回复没有这一行。
- 槽位只直接给出 `messageId` 和 `sessionId`。轮次号和 seq 通过 `useChat` 从该轮的 turn-tail 数据取得：`{ turn, seq, closing.finalNode.{ seq, messageId } }`，其中 `seq` 是该轮 `turn/end` 事件的序号，分叉按钮用的也是它。该轮的起始 seq 来自轮次投影。
- 复制的内容是一段人和模型都能读的 Markdown 链接：

```text
[「记忆系统设计」第 14 轮 · 11-09 23:05](dsh://session/session-3f2a91c0-…/1520..1610)
```

比纯 URI 多约 20 tokens，换来用户自己的消息里也看得懂引用的是什么。采用这一格式已确认（第 14 节问题 9）。

**会话菜单的“复制会话引用”。** 用 `ctx.contextMenus.register({ target: 'session', … })` 注册，`order: 460`，紧跟“复制 Session ID”（450）之后。会话目标的值是 `{ sessionId, displayTitle }`，正好用于生成 `[「标题」](dsh://session/<id>)`。参照 `packages/client/ui-workspace/src/client/session-actions/context-menus.tsx`。

**右侧栏“记忆”页。** 注册一个右侧栏标签类型（`ctx.sidebarRightTabs` 加对应的键控槽位），显示当前工作区和当前会话的规则与笔记，允许用户直接编辑和删除。用户对工作区记忆的编辑按外部修改处理（第 6.3 节），写入修改日志；对会话记忆的编辑按第 5.3 节中界面修改的记录方式记录。每篇会话笔记旁有“提升到工作区”按钮（第 8.5 节）。这一页还放健康信号、“整理”按钮（第 8.9 节）、工作区级开关，以及“清空本会话记忆”“删除工作区记忆”两个操作（第 4.7 节）。模型每次写记忆在对话里本来就有工具卡片，用户随时看得到它记了什么。

**开关入口（第 4.7 节）。**

- 全局：插件设置页，即 DSH 为插件配置字段生成的设置表单。
- 工作区：“记忆”页顶部，以及工作区右键菜单中的“记忆设置”（`ctx.contextMenus`，`target: 'workspace'`）。
- 会话：输入框工具行的一个小控件，与计划模式、权限控件同一行（列表槽位 `conversation.input.left`，会话作用域），点开后是本会话的四个开关；新开对话时 DSH 已创建空白会话，所以发出第一条消息前就能设置。“记忆”页中也可修改。

**与现有会话引用的关系。** DSH 的 `dsh-session-reference` 已支持在输入框里 `@` 一个会话，格式为 `@[标题](dsh-session:<base64url(JSON 字符串化的 id)>)`。它的语义是“程序注入”：发送时 Host 自动插入一条消息，内含被引用会话可见消息的 JSON 预览，每个来源上限为 64 KiB 与上下文窗口的一定比例中的较大者，最多三个来源。本插件的 `dsh://` 引用只是指针，粘贴后不触发任何注入，由模型决定读不读、读多少。两者可以共存：`memory_view` 也接受 `dsh-session:` URI，解码后按会话引用处理。DSH 目前没有“复制消息链接”这类功能，也没有消息级或 seq 级的引用语法。

## 11 Token 与缓存成本

### 11.1 价格结构决定优化方向

DeepSeek 官方价格页（2026 年 11 月 10 日查询），单位为美元/百万 tokens，非高峰时段：

| 模型                                | 输入（缓存命中） | 输入（缓存未命中） | 输出 |
| ----------------------------------- | ---------------- | ------------------ | ---- |
| `deepseek-flash`（V4.1-Flash-1017） | 0.003            | 0.15               | 0.6  |
| `deepseek-v4-pro`（V4-Pro-0813）    | 0.022            | 0.66               | 1.98 |

高峰时段价格翻倍。缓存命中价约为未命中的 1/50（Flash）和 1/30（Pro），输出约为未命中输入的 3 至 4 倍。缓存按“前缀单元”匹配，单元在每次请求的用户输入末尾、模型输出末尾以及公共前缀处生成，属于尽力而为，未使用的缓存几小时到几天内清除（[DeepSeek 上下文缓存文档](https://api-docs.deepseek.com/guides/kv_cache/)）。

由此得到四条优化顺序：

1. **少写输出。** 记忆写入是输出 token，最贵。笔记写短，索引机械生成，不要求模型为了维护目录额外写一次。
2. **新增输入要小。** 检索结果第一次进入上下文按未命中计价，之后留在历史里按命中计价，但会占上下文窗口、让压缩提前到来；压缩本身要一次摘要调用，并让替换点之后的前缀失效。因此工具结果默认精简，大输出分段续读。
3. **前缀不变。** 静态说明和工具 schema 一旦命中缓存，每次请求的成本可以忽略；但只要其中有一个字节因会话而异，所有会话都要付未命中价。
4. **常驻内容只付一次。** 常驻快照在会话首个请求和每次压缩后各付一次未命中价，其余请求都是命中价。

### 11.2 估算

| 项                         | 位置         | 估计量                      | 计价                                           |
| -------------------------- | ------------ | --------------------------- | ---------------------------------------------- |
| 静态使用说明               | 系统提示     | 约 350 tokens               | 首次未命中，之后命中                           |
| 两个工具 schema            | 工具声明     | 约 600 tokens               | 同上                                           |
| 常驻快照                   | 历史中，追加 | 0.5K 至 5K tokens           | 每会话首次与每次压缩后未命中一次               |
| 外部修改增量               | 历史中，追加 | 50 至 150 tokens/次         | 未命中一次                                     |
| 分叉位置通知               | 历史中，追加 | 约 40 tokens                | 未命中一次                                     |
| 一次找回                   | 工具结果     | 1K 至 6K tokens             | 未命中一次                                     |
| 一次写笔记                 | 工具调用参数 | 100 至 400 tokens           | 输出价                                         |
| 一次整理会话（100 篇笔记） | 独立会话     | 约 40K 输入、5K 至 10K 输出 | Flash 约 $0.01，Pro 约 $0.05，用户触发时才发生 |
| 找回时补写一条决策指针     | 工具调用参数 | 约 300 tokens               | 输出价，Pro 约 $0.0006                         |
| 会话笔记的写入提示         | 工具结果     | 约 25 tokens/次             | 未命中一次，只在会话级写入时出现               |

不使用记忆时，用户为了让新会话接上昨晚的讨论，通常要重新描述或粘贴大段内容，这部分是未命中输入，还要模型重新理解。找回 3K 至 6K tokens 的原文在大多数情况下更便宜，也更准确。这个判断需要第 13 节的评估验证，本文不预设节约比例。

### 11.3 测量

DSH 的 `ctx.tokenMeter` 和响应中的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` 字段足以分项统计。评估时分别报告 token、费用和延迟，缓存折扣不能当成 token 减少来报告。

## 12 场景走查

**A. 昨晚的讨论。** 见第 7.2 节。没有任何笔记时靠机械目录、压缩摘要和原文；第一次这样找回后补写决策指针，之后一次读取即可。

**B. “此处无需校验 checksum”。** 模型先按第 3.1 节判断：

- 如果“此处”是代码里的某个校验点，并且以后的 Agent 很可能再把校验加回去，最合适的载体是代码本身：删掉校验，并在原位写一句描述当前约束的注释（“资源包来自已签名的内部制品库，此处不校验 checksum”）。仓库表达了这条事实，不进记忆。
- 如果当前指令不允许改那段代码，或者“此处”指的是一个操作流程而非代码位置，就写规则，并写清对象：“`scripts/fetch-assets.ts` 下载的离线资源包无需校验 checksum”。用户在讨论这个分支的临时方案时说的，写会话规则；说的是这个项目的长期做法，写工作区规则。
- 不能写成“无需校验 checksum”。

**C. “以后简单修改无需回归测试”。** 写工作区规则，保留“简单修改”并给出可判断的边界。写之前读仓库 `AGENTS.md`：若其中要求所有修改都跑回归测试，仓库优先，规则写了也不生效。模型应告诉用户冲突，问是否修改 `AGENTS.md`。

**D. 踩坑。** 模型在构建上花了二十分钟，最后发现是 Windows 下缓存导致产物过期。它判断这不是偶然失误，换个会话还会遇到，于是写 `/notes/win-pnpm-cache.md`（类型 `lesson`），`sources` 指向得出结论的那几次命令输出。索引里自动多出一行。下次任何会话在 Windows 上构建出问题，常驻索引里就能看到这条。

**E. 分叉。** 会话 A 第 12 轮后分叉出 B。B 继承 A 截至第 12 轮的会话规则和笔记；A 之后加的会话规则不进入 B；B 自己加的也不影响 A。两者看到同一份工作区规则。B 想参考 A 后来的会话规则，读 `../<A>/RULES.md`，读到的内容标明来源，不会成为 B 的规则。B 的首个请求命中 A 的缓存前缀，只多一条位置通知。

**F. 压缩。** 会话进行到第 60 轮触发压缩，前 50 轮被替换成摘要，其中包括第 20 轮写会话规则的那次工具调用。下一个请求前，比对发现“看得到的版本”已经回退，插件注入一份最新的完整快照，末尾注明被压缩的 seq 范围。模型若需要被压缩部分的细节，直接读 `./log/…`。

**G. 并发修改。** 会话 A 和 B 同时运行。用户在 A 里说“以后提交信息用英文”，A 写入工作区规则。B 的下一个请求前收到一条增量通知。若 B 恰好也在改 `RULES.md`，B 的 `edit` 因文件哈希变化失败，B 重新读取后再改。

### 13.2 模型行为评估（固定任务集，重复运行）

基线为“只有原始记录查询，没有常驻层和笔记”。任务覆盖：找回讨论（含高代价找回后是否补写指针、第二次找回是否走指针）、笔记作用域是否选对（跨会话成立的内容是否写进工作区，用到别的会话的笔记后是否提升）、持续规则遵守、局部例外不被扩大、代码变化后旧笔记不覆盖当前事实、分叉探索、反复踩坑、模糊请求时是否提问、只读索引能否照做（任务的答案就在某篇笔记里，记录模型是否打开正文、不打开时是否做对；同时检查模型新写的 description 是不是结论、一篇是否只记一个事实）。指标：找回成功率、规则遵守率、仅凭索引的正确率、错误扩大率、虚构来源率、总输入与输出 tokens、命中与未命中 tokens、费用、调用次数与延迟。若某一层（例如决策指针）没有带来可测量的收益，就删掉它，而不是为了结构完整保留。

## 14 关键选择

以下选择均已与用户确认，每项写明理由和未采用的备选。正文其他章节以“第 14 节问题 N”引用这些条目。

**问题 1（已确认）：规则继承默认叠加。** 会话规则加在工作区规则之上，个别例外用自然语言写在会话规则里；整体停用由会话级开关“继承工作区记忆”表达（第 14 节问题 14），规则文件不再有 `inherit: false` 标记；`@` 用于把一篇笔记并入规则。理由见第 6.2 节；Codex、Claude Code 和 DSH 自己的 `AGENTS.md` 加载也都是逐级拼接。

**问题 2（已确认）：外部修改的规则在下一个请求生效。** 其他会话或用户改了规则，正在运行的会话在下一个请求前收到追加式增量通知，约 50 至 150 tokens。Claude Code 和 Hermes 选择冻结到压缩或新会话，是因为它们把记忆放在紧跟系统提示的位置，中途改动会破坏缓存；本设计的增量追加在历史末尾，没有这个问题。Hermes 文档也承认长期运行的会话因冻结而很少看到新记忆。配置项 `externalRuleUpdates` 保留 `next-compaction` 供部署选用。

**问题 3（已确认）：索引由插件从笔记 frontmatter 机械生成。** 描述文字由模型写笔记时自己写，目录级 `README.md` 提供人工归类说明，不另设模型维护的 `INDEX.md`。理由：不会漏登记，每写一篇笔记省一次输出；OKF 也允许索引由消费方合成。代价是排序和分组只能按目录与类型，不能任意编排。

**问题 4（已确认）：子代理默认只读。** 能看到工作区规则和父会话规则，经验交回父会话决定是否记录。配置项 `subagentWrite` 可以放开写入；给子代理配独立记忆目录（Claude Code 的做法）暂不采用。

**问题 5（已确认）：不设用户层。** 跨工作区的个人偏好（“回复用中文”）的正本是 `~/.dsh/AGENTS.md`，由 `dsh-agent-instructions` 在每个会话加载。模型发现这类偏好时告诉用户，用户同意后可以代写。记忆系统的根仍是工作区，同一类事实不出现两个正本。

**问题 6（已确认）：会话记忆提交记录首版用工具结果元数据（方案 A）。** PTC 预设下的嵌套调用走 `deferContext` 补充路径；DSH 接受外部插件声明仅日志事件后，再评估统一为方案 B。

**问题 7（已确认）：首版不建全文索引。** 检索用时间窗收窄加字面扫描；第二阶段是否加入 trigram 全文索引，以实测扫描耗时为准，加入后字面扫描仍保留为回退。

**问题 8（已确认）：不做压缩前或定期提醒；决策指针由模型在讨论形成结论时自行判断，并在高代价找回后补写；压缩摘要作为检索渠道。** 依据（V4-Pro 非高峰价，上下文 10 万 tokens 时的估算）：

- 一次提醒多花约 $0.003（没写东西）至 $0.007（写了一篇指针），与一次压缩的摘要调用（约 $0.008）同量级；上下文越长，命中部分越贵，50 万 tokens 时约 $0.025。
- 指针在讨论被再次引用时省约 $0.005 至 0.04，长讨论省得最多；只有被提醒过的讨论里约三成以后真被引用，提醒才在费用上持平。
- 比费用更关键的是：结论通常出现在讨论结束时，而压缩发生在上下文满时，两者不对应，很多晚间讨论整个会话都不压缩，提醒根本不会触发；DSH 的压缩发生在任务进行中，插入提醒会打断当前工作；DSH 也没有在压缩前运行一次模型的扩展点；提醒还会诱导低价值笔记，挤占常驻索引。
- 找回时补写只在讨论真被引用时付约 300 输出 tokens（约 $0.0006），第二次起找回只需一次读取。
- 压缩摘要由 DSH 的压缩指令生成，固定包含“决策及其理由”一节，读取不需要额外生成。

第二阶段可选：由用户触发的“记下这次讨论的结论”按钮或命令，用户点了才写。

**问题 9（已确认）：复制引用生成带标题和时间的 Markdown 链接。** 例如 `[「记忆系统设计」第 14 轮 · 11-09 23:05](dsh://session/…/1520..1610)`，比纯 URI 多约 20 tokens，用户自己的消息里也看得懂引用的是哪段讨论。格式见第 4.3 节和第 10.3 节。

**问题 10（已确认）：路径作用域的规则放到第二阶段。** 这类规则带文件匹配模式，只在模型读写匹配文件时注入，平时不占常驻预算；Claude Code 的 `.claude/rules` 和 DSH 子目录 `AGENTS.md` 的按需加载都是这种做法。代价是要跟踪模型读写过的文件，且压缩后要再次碰到匹配文件才恢复。首版规则量小，常驻预算够用，实测出预算吃紧再做。

**问题 11（已确认）：整理的时机与方式。** 四个时机：写规则超预算时当场合并，读到过时或重复的笔记时顺手修正，索引开始折叠时提示，用户点“整理”时开整理会话。整理会话先出计划，用户确认一次后执行，规则逐条确认。整理后，规则在下一个请求生效；笔记与索引等下次完整注入，期间旧路径经重定向可用（第 8.9 节）。未采用：定期自动整理；先执行、事后回滚；写入时的疑似重复提示和“疑似重复笔记对数”这一健康指标。重复由模型在使用中发现、由整理会话处理，不由程序做字面判定。

**问题 12（已确认）：三级开关。** 记忆总开关分全局、工作区、会话三级；“允许写入”分工作区、会话两级；“其他会话可检索本会话”和“继承工作区记忆”（问题 14）只在会话级。全局是硬总闸，工作区与会话为“跟随上级、开、关”三态，会话优先。会话开始时即为关闭的，等效于未安装插件，不注册使用说明和工具定义；会话设置因此存放在插件存储域，不写进会话日志（第 4.7 节）。未采用：关闭时仍保留使用说明和工具定义以共享初始缓存。那样“关闭”的会话仍能看到记忆工具，破坏语义，而省下的只是少量缓存命中费用。会话进行中关闭时保留已注册的说明和工具，只追加关闭通知、工具返回“已关闭”；未采用中途也撤掉说明和工具，因为那会在会话中途改写系统提示和工具声明，而这一轮之前的历史里本来就有记忆内容，撤掉也做不到真正的“未安装”。

**问题 13（已确认）：笔记默认写工作区。** 判断标准是“离开这个会话，它还成立吗”；只在本会话或本分支成立的内容才写会话笔记（第 3.1 节）。为防有价值的内容留在会话里，加三处补救（第 8.5 节）：写入会话笔记时提示一次；会话清单显示每个会话的规则与笔记数量，搜索 `/sessions` 时覆盖会话笔记；跨会话用到某篇会话笔记后把它提升为工作区笔记，记忆页也提供提升按钮。未采用：工具层面设默认作用域（保留“路径里写明作用域”，避免模型不经判断就落在默认值上）；把其他会话的会话笔记也列进索引（会让索引随兄弟会话变化，并模糊分支独立的语义）。

**问题 14（已确认）：干净会话。** 会话级开关“继承工作区记忆”，默认开；关闭后不加载工作区规则和工作区笔记索引，本会话的记忆、工具和按要求的检索照常可用（第 4.7 节）。发出第一条消息前即可设置，第一个请求之前的任何开关变化都不通知模型。它取代了会话规则文件中的 `inherit: false`：后者只停规则不停索引，写在模型维护的文件里，对话开始前也设不了。未采用：两者并存（会出现文件与开关不一致时以谁为准的问题）；用记忆总开关代替（等效于未安装，本会话也无法记忆和检索）。

**问题 15（已确认）：description 写这篇笔记最重要的那句结论，一篇笔记只记一个事实。** 索引每个请求都在上下文里，正文按需打开，description 是模型多数时候唯一读到的部分。本设计的索引直接由 description 生成（问题 3），不像 Claude Code 的 `MEMORY.md` 那样另有一行由模型单独编写；description 只写主题，索引就只剩主题。用户以 Claude Code 自动记忆中的一篇为例：description 是“用户偏好标准库优先、少依赖、按单用户本地场景做最简设计，不要过度工程化”，模型不打开文件，只读索引就得到约八成信息。同一篇的正文还有第二段独立的产品原则（“小说不是游戏”，平台不替故事裁决能不能发生），description 没有覆盖，只读索引的模型看不到它，这就是“一篇一事”的理由。写法与拆分标准见第 8.2 节，整理会话负责拆分和改写描述（第 8.9 节），静态说明各有一句（第 9.3 节）。description 与正文的同步也只靠静态说明里的那一句：笔记是普通文件，`memory_write` 不区分 frontmatter 和正文，模型改正文结论时用同一次 `edit` 或 `replace` 就能改 description。未采用：放宽字数，让一句 description 概括几个事实（索引预算按篇累加，描述越长索引越早折叠）；由程序检测“主题式”描述（字面判断不可靠，理由同问题 11 不做疑似重复判定）；正文变了而 description 没变时，在写入结果里附提醒（静态说明已经覆盖，不再加一层机制）。

## 15 参考设计与取舍

### 15.1 DeepSeek Harness 自身

DSH 的文档规范已经写明“只描述当前状态，历史放在提交、PR、决策记录（Agent Notes）和事故复盘里”（`docs/AGENTS.md` 的 Document current state 一条），`.agents/notes/` 按 `proposed`、`implemented`、`rejected`、`archived` 管理决策记录。第 3.2 节的方法论与它一致，可以直接引用为范例。

`dsh-agent-instructions` 是常驻层最直接的参照：带来源的 `user/message`、按可见状态比对、压缩后恢复、追加式更新、预算内先省略宽泛文件再截断最具体文件。本设计在它之上增加“本会话自己的写入不重发”。

### 15.2 Codex

Codex 在启动时读全局文件，再从项目根到当前目录逐级读取，“从根向下拼接，以空行分隔”，越靠近当前目录的内容越靠后、效果上越优先。同一目录下的 `AGENTS.override.md` 取代该目录的 `AGENTS.md`，上级目录的文件仍然拼接。默认叠加、显式取代、取代只作用于本级，与第 6.2 节的选择一致。合并后的总量默认上限 32 KiB，超出即停止追加。（[Codex：AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)）

### 15.3 Claude Code

依据 code.claude.com 的 [memory](https://code.claude.com/docs/en/memory)、[context-window](https://code.claude.com/docs/en/context-window)、[prompt-caching](https://code.claude.com/docs/en/prompt-caching)、[sessions](https://code.claude.com/docs/en/sessions)、[sub-agents](https://code.claude.com/docs/en/sub-agents) 页面。

| 机制           | Claude Code 的做法                                                                                                                                                                                                                                                          | 本设计                                                                     |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 指导文件层级   | 托管策略、`~/.claude/CLAUDE.md`、项目 `CLAUDE.md`、`CLAUDE.local.md`，从根到当前目录拼接；子目录的文件在读写该目录文件时才加载                                                                                                                                              | 仓库指导文件交给 `dsh-agent-instructions`，记忆系统不重复                  |
| `@` 导入       | 相对所在文件解析，最多四跳，跳过代码片段                                                                                                                                                                                                                                    | 只在 `RULES.md` 中展开，一层                                               |
| 路径作用域规则 | `.claude/rules/*.md` 的 `paths` 匹配到被读写的文件时才加载；压缩后要再次触碰匹配文件才恢复                                                                                                                                                                                  | 第二阶段再做（第 14 节问题 10）                                            |
| 自动记忆       | `~/.claude/projects/<project>/memory/`，按 Git 仓库归属；`MEMORY.md` 每行一条，每个会话加载前 200 行或 25 KB；主题文件按需用普通文件工具读取；超出上限时写入仍成功但返回错误要求重写索引；笔记 `type` 为 `user`、`feedback`、`project`、`reference`；可从代码推出的内容不记 | 两层结构相同；索引从 frontmatter 机械生成（问题 3）；按 `WorkspaceId` 归属 |
| 注入位置       | `CLAUDE.md` 作为系统提示之后的用户消息注入，不在系统提示内                                                                                                                                                                                                                  | 相同，且放在保留历史之后                                                   |
| 会话中途修改   | 会话开始时读一次；修改要到 `/clear`、`/compact` 或重启才生效，以免破坏缓存                                                                                                                                                                                                  | 本会话自己的修改不重发；外部修改发追加式增量（问题 2）                     |
| 压缩后         | 项目根 `CLAUDE.md`、无路径规则和自动记忆从磁盘重新注入                                                                                                                                                                                                                      | 相同                                                                       |
| 子代理         | 主自动记忆不加载到子代理（分叉出的除外）；子代理可配置独立的记忆目录                                                                                                                                                                                                        | 子代理只读继承工作区与父会话规则（问题 4）                                 |
| 原始记录       | `~/.claude/projects/<project>/<session-id>.jsonl`，默认保留 30 天；没有供模型搜索历史会话的内置工具                                                                                                                                                                         | 原始记录永久可读，并有浏览与搜索工具，这是本设计的核心差异                 |

调研中检索到的 issue 标题（未逐一打开核实）反映了两类问题：压缩后规则不再被遵守，以及自动记忆的优先级压过项目指令。前者对应本设计压缩后的完整重注入，后者对应第 6.2 节“仓库指导文件高于记忆规则”。

### 15.4 Hermes Agent

依据 [Hermes 记忆文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory) 与 `NousResearch/hermes-agent` 源码（提交 `8a2adc7`）。

- `MEMORY.md` 上限 2,200 字符，`USER.md` 上限 1,375 字符，头部显示用量百分比。满了不自动压缩，写入报出超出量，要求模型一次性整理。本设计的预算拒绝与此相同。
- `memory` 工具只有 `add`、`patch`、`remove` 和批量操作，故意没有 `replace`：模型曾把 `replace` 当查找替换用，抹掉了同一条目里的其他事实。本设计因此要求整体覆盖返回被删除的行（第 8.3 节）。
- 会话开始时冻结快照，写入立即落盘但下个会话才进系统提示，目的是保护前缀缓存；源码显示压缩后会从磁盘重载。文档同时指出，消息网关里的对话可能“连续数周是同一个会话”，因而很少看到新记忆。这是第 14 节问题 2 采用追加增量的依据之一。
- `session_search` 基于 SQLite FTS5，不调用模型做摘要；默认返回 3 个会话，按谱系去重，隐藏子代理和工具会话，单条消息截断到 1,200 至 4,000 字符。本设计的结果上限可参考这些默认值。
- 每 10 个用户轮次触发一次后台复查分支，在另一个线程里用更便宜的模型写记忆和技能，不改动主对话。本设计首版不做定期提醒（问题 8），这一做法可作为以后的可选项。
- 技能是程序性记忆，三级渐进披露：列表、正文、单个附件。可复用的多步操作在 DSH 里也更适合写成技能而不是笔记。

### 15.5 OKF v0.2

依据 [OKF SPEC.md](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md)。OKF 是面向知识库的格式：Markdown 加 YAML frontmatter，`type` 是唯一必填字段，`description` 是一句话、供索引复用；每级目录保留 `index.md`（条目格式 `* [标题](url) - 描述`，可以由生产者生成，也可以由消费者合成）和 `log.md`（按日期倒序的历史）；来源写在 `sources[]`，正文用脚注 `[^id]` 引用；信任用 `generated`、`verified` 表达；状态为 `draft`、`stable`、`deprecated`，另有 `stale_after`。它明确不规定存储、服务和查询设施。

本设计借鉴了 `type`、`description`、`sources`、`verified`、`status`，以及“索引可以机械合成”“历史放进专门的日志”两点；没有采用每级 `index.md` 和脚注引用，因为会话和分支语义、常驻规则和上下文恢复都不在 OKF 的范围内，而且脚注会增加每篇笔记的 token。本设计不声称兼容 OKF，需要导出时字段可以直接映射。

### 15.6 其他

- **Codex memories**：默认关闭，后台从空闲的历史对话中提取，再由整合子代理更新 `MEMORY.md`。文档明确要求“团队必须遵守的指导放在 `AGENTS.md`”。（[文档](https://learn.chatgpt.com/docs/customization/memories)）
- **Letta**：常驻上下文的记忆块（可用工具编辑）与上下文之外的归档记忆（插入与搜索）两层，与本设计的 L0、L1 对应。（[文档](https://docs.letta.com/guides/agents/context-hierarchy)）
